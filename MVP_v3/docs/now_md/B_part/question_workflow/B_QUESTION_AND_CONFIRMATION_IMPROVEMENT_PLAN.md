# B Part — 질문 추천·확인 사실·대화 UX 개선 계획

작성일: 2026-09-21
상태: 작업 계획 확정 / 구현 전

---

## 1. 문서 목적

이 문서는 CSR(Case Share Room) B Part의 남은 개선 작업을 하나의 기준으로 정리합니다.

핵심 목표는 다음과 같습니다.

- Case 생성 시 이미 확보된 정보를 반영해 불필요한 재질문을 줄입니다.
- 아직 확인되지 않은 중요 정보를 단계와 우선순위에 따라 추천 질문으로 생성합니다.
- 은행 담당자가 확인한 사실을 Case Context에 안전하게 반영합니다.
- Quality/Grounding 차단 상황에서도 단순 오류 대신 현재 상태를 설명하는 AI 응답을 제공합니다.
- 질문·답변 기록을 Bank ROOM에서 더 읽기 쉽게 정리합니다.
- Bank AI 대화와 기존 고객 확인 질문 기능을 연결합니다.

AI는 최종 판단자가 아니라 질문 추천, 사실 구조화, 상태 설명을 통해 담당자의 확인과 판단을 지원합니다.

---

## 2. 전체 개선 흐름

```text
질문 매뉴얼
→ Case 생성
→ 현재 연결된 diagnosis / Case Context / 기존 질문·답변·Fact·Verification·Action 확인
→ 활용 가능한 STT / FDS Evidence의 출처·연결 여부 확인
→ 이미 충분히 확인된 Target 제외
→ 현재 단계의 미확인 Target 계산
→ 우선순위 기반 추천 질문 생성
→ 담당자 검토·수정
→ 고객 전달
→ 고객 응답
→ Case Context 반영
→ 담당자 확인 사실 반영
→ 다음 질문 / Verification 갱신
```

질문은 문장보다 `canonical target`을 중심으로 관리합니다.

1차 자동 추천에서 사용할 현재 Target 예:

```text
transfer_status
authentication_information_exposure
personal_information_exposure
remote_control_app
transfer_purpose
claimed_organization
incident_claim
```

다음은 매뉴얼상의 `UNMAPPED` 후보입니다: `ongoing_contact`, `credential_exposure`, `device_compromise`, `impersonated_entity`, `contact_method`, `evidence_available`. 1차 자동 추천에 직접 사용하지 않고, 별도 mapping·설계 결정 후 연결합니다. 새 enum·alias·target을 이 계획에서 확정하지 않습니다.

같은 Target이 이미 충분히 확인되었다면 표현만 다른 질문을 다시 생성하지 않습니다.
`claimed_organization`과 `impersonated_institution`은 코드 alias가 아니지만 동일한 사칭 대상 정보를 묻는 경우 conceptual duplicate로 검토합니다. `remote_control_app`에서는 앱 설치 요구와 실제 설치를 서로 다른 사실로 구분합니다. 두 기준의 실제 추천·저장 처리는 1번 구현 단계에서 검토합니다.

---

## 3. 공통 원칙

- AI 추천 질문은 담당자 검토 없이 고객에게 자동 전송하지 않습니다.
- Case 생성 시 1단계 질문은 자동 준비할 수 있지만 자동 발송하지 않습니다.
- `PROPOSED != CONFIRMED`
- `CUSTOMER_STATEMENT != VERIFIED FACT`
- `ANSWERED != SUFFICIENT`
- `UNKNOWN != FALSE`
- 고객에게 다시 물어볼 필요가 없는 것과 객관적으로 검증된 사실은 구분합니다.
- Evidence에 없는 내용을 AI가 새 사실로 만들지 않습니다.
- Quality/Grounding 기준을 단순히 완화해 오류를 숨기지 않습니다.
- 기존 기능을 재사용할 수 있으면 별도 기능을 중복 구현하지 않습니다.

# 4. 작업 항목

## 0. CSR 질문 매뉴얼 작성

### 목표

추천 질문 생성의 기준이 되는 `CSR 확인 질문 매뉴얼`을 작성합니다.

매뉴얼에는 최소한 다음을 정의합니다.

```text
Target
단계
우선순위
질문 목적
ask_when
skip_when
sufficient_answer
follow-up
관련 보이스피싱 유형
근거 출처
```

질문은 `무조건 물어야 하는 질문`이 아니라 `반드시 확인해야 하는 정보`로 정의합니다.

예:

```text
transfer_status는 반드시 확인해야 하지만,
출처와 상태가 확인된 고객의 명확한 "송금하지 않았다"는 진술이
이미 같은 Target에 연결됐다면 같은 질문을 다시 생성하지 않습니다.
```

### 확정된 질문 4단계

```text
1단계: 즉시 피해 확대 여부 확인
2단계: 피해 범위와 행동 구체화
3단계: 사칭·접촉·사건 맥락 확인
4단계: Verification 및 후속 확인
```

단계와 현재 Target 배치는 `B_QUESTION_MANUAL.md`를 기준으로 합니다. 4단계는 새 기본 질문 Target을 추가하지 않고 `UNCERTAIN` 답변, `qf1` 후속 질문, `CONFLICT` 정보와 기존 Verification 결과를 검토합니다.

1단계 질문은 Case 생성 직후 자동 준비할 수 있지만 담당자 검토 전 고객에게 자동 전송하지 않습니다.

## 1. 매뉴얼 + Case Context 기반 추천 질문 생성

### 목표

질문 매뉴얼과 실제 Case 데이터를 함께 사용해 현재 Case에서 필요한 질문만 추천합니다.

### 주요 입력

- 질문 매뉴얼
- diagnosis
- Case Context
- 기존 QUESTION / ANSWER
- Fact / Verification / Action
- 일부 최근 고객·직원 MESSAGE / Case 검색 결과
- 기존 AI 추천 질문
- canonical target 상태

STT 원문과 별도 FDS 자료는 활용 가능한 Evidence 후보입니다. 현재 질문 추천 경로에 직접 연결됐다고 단정하지 않으며, 입력 경계와 Target·출처 연결은 구현 단계에서 확인합니다.

### 처리 흐름

```text
매뉴얼 Target
→ 현재 Case 상태 확인
→ 이미 충분히 해결된 Target 제외
→ 기존 PENDING / ASKED / ANSWERED 상태 확인
→ 의미 중복 제거
→ 현재 단계 Target 선정
→ 우선순위 계산
→ 질문 생성
→ 담당자에게 추천
```

현재 Case에 필요한 질문 후보 전체 수에는 임의의 고정 상한을 두지 않습니다. 충분히 확인된 Target, 활성 질문, 의미 중복을 제외한 뒤 유효 후보를 계산합니다.

담당자 화면에 한 번에 보여주는 추천 묶음은 **기본 5개**입니다. 이는 전체 후보 수의 최대치가 아닙니다. 필요한 후보가 2개면 2개만 표시하고, 5개를 넘는 유효 후보는 버리지 않고 추가 후보로 유지해 이후 확인할 수 있게 합니다. 묶음 크기를 채우기 위해 불필요한 질문을 생성하지 않습니다. 구체적인 추가 후보 UI 방식은 구현 단계에서 정합니다.

### Case 생성 시 초기 질문

Case 생성 직후 1단계 Target 기준으로 초기 추천 질문을 자동 준비합니다.

```text
자동 생성/준비: 허용
자동 고객 전송: 금지
```

담당자가 확인·수정·선택한 질문만 고객에게 전달합니다.

## 2. 직원 확인 사실 반영 및 AI 응답 안정화

### 2-1. Quality 차단 상황에서도 설명형 AI_RESPONSE 제공

#### 현재 문제

예:

```text
고객:
본인은 이종열이라고 말함.

은행 직원:
내가 신원 확인해보니까 이종열이 맞아.
```

현재 직원 발화가 저장되어도 Case Fact가 `CONFIRMED`로 반영되지 않을 수 있습니다.

이 상태에서 AI가 확정적으로 응답하려 하면 `unsupported_certainty`에 의해 차단되어 503과 오류 메시지만 표시될 수 있습니다.

#### 개선 목표

정상 입력이 들어왔을 때 단순 오류로 끝내지 않습니다.

Quality/Grounding 기준 때문에 확정 표현을 사용할 수 없는 경우에도 현재 상태와 다음 행동을 설명하는 안전한 AI_RESPONSE를 제공합니다.

예:

```text
담당자가 고객 이름이 이종열이라고 확인했다고 입력했습니다.
다만 현재 이 내용은 Case의 CONFIRMED 사실로 아직 반영되지 않았습니다.
확인 사실로 등록되면 이후 답변에서는 확인된 정보로 사용할 수 있습니다.
```

핵심 흐름:

```text
확정 표현 불가
→ 현재 확인 상태 설명
→ 왜 확정할 수 없는지 설명
→ 다음 확인/등록 방법 안내
```

Quality/Grounding 기준을 우회하거나 Evidence에 없는 사실을 생성하지 않습니다.

---

### 2-2. 직원 확인 사실을 CONFIRMED 후보로 구조화

### 목표

은행 담당자가 확인한 사실을 일반 MESSAGE에만 남기지 않고 Case Context에 반영할 수 있게 합니다.

예:

```text
담당자:
신원 확인 완료. 고객 이름은 이종열이 맞습니다.
```

확인 사실 후보는 다음 정보를 가질 수 있습니다.

```text
target
value
source
source_message_id
confirmed_by
confirmed_at
status
```

### 상태 원칙

```text
CONFIRMED
= 담당자가 확인했다고 명시적으로 기록한 사실

VERIFIED
= 공식 시스템 / 별도 Evidence 등을 통해 검증된 사실
```

`CONFIRMED`를 자동으로 `VERIFIED`로 승격하지 않습니다.

초기 구현에서는 자유로운 은행 내부 채팅을 LLM이 해석했다는 이유만으로 즉시 `CONFIRMED`로 만들지 않습니다.

```text
직원 발화
→ 직원 확인 사실 후보 추출
→ 담당자 확인 절차
→ CONFIRMED
```

명확한 확인 표현만 자동 처리할 수 있는지는 이후 별도로 검토합니다.

---

### 2-3. 은행 담당자용 확인 사실 카드

### 목표

고객이 별도로 답하지 않았더라도 은행 담당자가 다른 경로로 확인한 사실을 Case Context에 반영할 수 있게 합니다.

AI가 현재 Case를 기준으로 확인 후보를 생성합니다.

예:

```text
고객 이름이 이종열로 확인됐나요?
[확인됨] [아님] [아직 미확인]

실제 송금은 하지 않은 것으로 확인됐나요?
[확인됨] [아님] [아직 미확인]
```

`아님`과 `미확인`은 구분합니다.

예:

```text
"고객 이름이 이종열인가?"
→ 아님
```

만으로 실제 고객 이름을 알 수 없으므로 다른 값을 자동 생성하지 않습니다.

### 담당자 직접 입력

AI가 생성하지 않은 사실도 담당자가 직접 추가할 수 있게 합니다.

입력 후보:

```text
확인 Target
확인 값
근거/메모
```

시스템은 함께 다음 정보를 보존합니다.

```text
confirmed_by
confirmed_at
source
```

등록된 정보는 적절한 provenance와 함께 `CONFIRMED` Fact로 관리합니다.

## 3. 질문 발송·답변 카드 UI 정리

### 3-1. 여러 질문 발송 기록 묶기

여러 질문을 한 번에 전송했을 때 Bank ROOM에서는 하나의 발송 기록으로 묶습니다.

기본 상태:

```text
고객 확인 질문 4건 발송됨
[펼치기]
```

펼친 상태:

```text
고객 확인 질문 4건 발송됨
[접기]

1. 인증번호, 비밀번호 또는 OTP를 제공하셨나요?
2. 개인정보를 제공하셨나요?
3. 실제로 송금하거나 이체하셨나요?
4. 원격제어 또는 화면공유 앱 설치 안내를 받으셨나요?
```

UI만 묶어서 표시하며 내부 질문 데이터는 계속 독립적으로 관리합니다.

```text
Question A → ASKED
Question B → ASKED
Question C → ASKED
Question D → ASKED
```

---

### 3-2. 고객 답변은 별도 Q&A 대화 이벤트로 표시

질문 발송 묶음은 `어떤 질문을 보냈는지` 보여주는 기록으로 유지합니다.

고객이 나중에 답변하면 기존 발송 묶음을 찾아 펼쳐보게 하지 않고, 답변 시점에 새로운 Q&A 이벤트를 표시합니다.

예:

```text
인증번호, 비밀번호 또는 OTP를 제공하셨나요?

잘 모르겠어요.
```

질문과 답변은 하나의 카드에 포함하고 현재 답변 카드의 `고객 답변` 라벨은 제거합니다.

Customer ROOM의 기존 `현재 질문 한 건씩 노출` 흐름은 유지합니다.

## 4. AI 답변 핵심 정리 표현 개선

### 목표

AI 답변 마지막에 현재 답변의 핵심을 빠르게 파악할 수 있는 요약을 제공합니다.

`결론`이라는 표현은 AI가 최종 판단을 내리는 것으로 오해될 수 있으므로 사용하지 않는 방향을 우선합니다.

추천 표현:

- 핵심 정리
- 현재 정리
- 다음 확인 포인트

예:

```text
현재 확인된 내용: ...
미확인 내용: ...

**핵심 정리: 현재 송금 여부가 확인되지 않았으므로
고객에게 실제 금전 전달 여부를 추가 확인할 필요가 있습니다.**
```

AI는 최종 사기 여부나 금융 조치를 결정하지 않습니다.

## 5. Bank AI 대화 ↔ 고객 확인 질문 기능 연동

### 목표

은행 내부 AI 대화에서 생성된 추천 질문을 기존 `고객에게 확인 질문` 기능으로 가져올 수 있게 합니다.

예:

```text
담당자:
추천하는 질문 있어?

AI:
1. 실제 송금 여부를 확인해보세요.
2. 인증정보 제공 여부를 확인해보세요.
3. 앱 설치 여부를 확인해보세요.

[고객 확인 질문으로 가져오기]
```

버튼 선택 시:

```text
Bank AI 추천 질문
→ 기존 고객 확인 질문 화면 열기
→ 추천 질문 후보 반영
→ 담당자 선택/수정
→ 고객 전달
```

AI 답변에서 바로 고객에게 자동 발송하지 않습니다.

가능하면 0번·1번에서 구축한 동일 질문 매뉴얼과 추천 로직을 재사용합니다.

## 6. AI 답변에서 다음 단계 Action 연결

### 목표

AI가 현재 Case 상태를 설명한 뒤 담당자가 다음 작업으로 빠르게 이동할 수 있도록 기존 기능을 연결합니다.

예:

```text
현재 송금 여부가 미확인 상태입니다.

[고객 확인 질문 만들기]
```

상황에 따라:

```text
[사건 정리]
[Verification 확인]
```

등을 연결할 수 있습니다.

이 기능은 0~5번 핵심 Workflow가 안정화된 뒤 마지막 확장 단계로 진행합니다.

AI가 강한 조치를 자동 실행하지 않으며, 버튼은 기존 기능으로 이동하거나 입력을 준비하는 역할을 우선합니다.

---

# 5. 작업 순서

```text
0. CSR 질문 매뉴얼 작성
↓
1. 매뉴얼 + Case Context 기반 추천 질문 생성
↓
2. 직원 확인 사실 반영 및 AI 응답 안정화
↓
3. 질문 발송·답변 카드 UI 정리
↓
4. AI 답변 핵심 정리 표현 개선
↓
5. Bank AI 대화 ↔ 고객 확인 질문 기능 연동
↓
6. AI 답변에서 다음 단계 Action 연결
```

순서 기준:

- `0`은 전체 추천 질문 작업의 기준입니다.
- `1`에서 질문 Target과 중복 제거 구조를 먼저 안정화합니다.
- `2`에서 확인 사실 상태를 안정화해야 `이미 확인된 Target 제외`가 정확해집니다.
- `3`은 안정화된 질문 데이터를 화면에 표시하는 작업입니다.
- `4`는 핵심 Workflow보다 표현 품질 개선에 가깝습니다.
- `5`는 1번의 추천 질문 기능을 Bank AI에서 재사용합니다.
- `6`은 여러 기능을 연결하는 확장 UX이므로 마지막에 진행합니다.

# 6. 공통 작업 방식

각 항목은 다음 순서를 기본으로 진행합니다.

```text
READ-ONLY 구조 확인
→ 현재 동작 / 영향 범위 정리
→ 변경 방향 확정
→ 최소 구현
→ 자동 테스트
→ Runtime/API 확인
→ 필요 시 MySQL 확인
→ Browser E2E 확인
→ 문서 상태 갱신
```

READ-ONLY 분석 중 발견한 개선안을 별도 결정 없이 자동 구현하지 않습니다.

# 7. 완료 / 검증 기준

## 질문 추천

- 출처·상태·Target 연결이 확인된 Evidence에서 이미 충분히 확인된 Target을 다시 추천하지 않음; STT 원문 연결 여부는 구현 단계에서 확인
- Customer answer에서 충분히 확인된 Target을 다시 추천하지 않음
- 기존 PENDING / ASKED 질문과 중복되지 않음
- 의미만 다른 동일 canonical target 질문을 중복 생성하지 않음
- 사칭 대상이 같은 `claimed_organization` / `impersonated_institution` 후보의 conceptual duplicate를 검토하되 코드 alias로 합치지 않음
- 현재 단계에 필요한 질문을 우선 추천
- 유효 후보 전체 수에 임의의 고정 상한을 두지 않음
- 담당자 화면은 기본 5개를 한 묶음으로 보여주고, 5개 초과 유효 후보는 버리지 않고 이후 확인 가능한 추가 후보로 유지
- 필요한 후보가 적으면 그 수만 표시하며 기본 5개를 채우기 위해 불필요한 질문을 생성하지 않음
- `UNMAPPED` 매뉴얼 후보는 1차 자동 추천에 직접 사용하지 않음
- 담당자 검토 전 고객 자동 전송 없음

## 직원 확인 사실 / AI 응답

- 직원 확인 정보를 일반 MESSAGE에만 남기지 않음
- 누가, 언제, 무엇을 확인했는지 provenance 유지
- `CONFIRMED`와 `VERIFIED` 구분
- `UNKNOWN`을 `FALSE`로 처리하지 않음
- 확정할 수 없는 내용 때문에 전체 AI 응답이 단순 오류로 끝나지 않음

## 질문 UI

- 같은 전송 batch의 질문은 한 묶음으로 표시
- 펼치기 전 `질문 N건 발송됨` 형태로 확인 가능
- 펼치면 실제 질문 목록 확인 가능
- 질문 lifecycle은 내부적으로 개별 유지
- 고객 답변은 답변 시점의 별도 Q&A 이벤트로 표시
- Q&A 이벤트에서 질문과 답변을 하나의 카드로 확인 가능
- `고객 답변` 라벨 제거
- Customer ROOM 한 질문씩 노출 흐름 유지

## 기능 연동

- Bank AI 추천 질문을 기존 고객 확인 질문 UI로 가져올 수 있음
- 추천 질문 자동 전송 없음
- 동일 질문 매뉴얼/추천 로직 재사용
- 다음 단계 Action은 기존 기능으로 연결하며 자동 강제 조치 없음

# 8. 회귀 방지 대상

다음 기존 기능은 이번 개선 과정에서 유지합니다.

- Bank 연속 메시지 batching
- Bank in-flight supersede
- Customer batching / supersede
- stale AI_RESPONSE 저장 방지
- `PENDING → ASKED → ANSWERED`
- QUESTION / ANSWER 데이터
- 고객 질문 한 건씩 노출
- Customer answer 저장
- qf1 parent / target / duplicate 보호
- 담당자 승인 전 자동 고객 전송 금지
- Case Context provenance
- Quality / Grounding 안전 경계

# 9. 미확정 사항

다음 내용은 구현 전에 별도 검토 후 확정합니다.

- 직원 일반 채팅에서 확인 사실 후보를 추출한 뒤 `CONFIRMED`로 승격하는 정확한 승인 절차
- 매우 명확한 직원 확인 표현을 향후 자동 `CONFIRMED`로 허용할지 여부
- 확인 사실 카드의 구체적인 UI 위치와 표현
- AI 답변 핵심 정리의 최종 UI 표현
