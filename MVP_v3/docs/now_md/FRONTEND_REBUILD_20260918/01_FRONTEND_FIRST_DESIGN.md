# 프론트엔드 우선 재설계 기획

## 1. 목표

기존 백엔드의 의미·계약 혼선을 새 화면에 그대로 전파하지 않고, 사람이 먼저 이해할 수 있는 프론트엔드 구조를 만든다.

이번 단계에서는 데이터 해석이나 LLM 호출을 구현하지 않는다. 화면 구획과 상태 표현을 정리하고, 이후 백엔드가 채워야 할 View Model을 확정하는 것이 목적이다.

## 2. 유지할 큰 틀

```text
┌──────────────────────────────────────────────┐
│ 사건 헤더                                     │
├──────────────┬─────────────────┬─────────────┤
│ 좌측 탐색/    │ 중앙 대화        │ 우측 사건    │
│ 사건 목록     │ 메시지 타임라인  │ 맥락 패널    │
└──────────────┴─────────────────┴─────────────┘
```

- 좌측: 사건 목록·탐색·사건 선택
- 중앙: 실제 채팅과 메시지 입력
- 우측: 향후 LLM 사건 맥락 projection이 들어갈 자리

폭·접기·리사이즈·메시지 입력은 유지한다.

## 3. 이번 foundation에서 제거하는 것

### 중앙

- 확인 질문 카드
- 고객 답변 카드
- 기관 확인 요청/결과 카드
- 담당자 업무 카드
- 최종 결과 보고서 카드
- 기술 이벤트 카드
- 기존 검토/채택/기각 카드

일반 고객 메시지·은행 내부 메시지·AI 메시지는 기존 말풍선 형태로 남긴다.

### 우측

- Fact 카드
- 제안/확정/기각 버튼
- 근거 카드
- 금액 합계 카드
- 확인 필요 배지
- 업무·고객 공유 입력 폼
- 기존 섹션별 데이터 표시 모양

우측에는 제목과 빈 레이아웃 영역만 남긴다.

## 4. 새 화면에서 지켜야 할 원칙

- 프론트엔드는 사실을 추론하지 않는다.
- 프론트엔드는 문장을 조립하지 않는다.
- 프론트엔드는 `display_text`를 그대로 표시한다.
- 확정 여부·근거 유효성·중복 통합은 백엔드 책임이다.
- 로딩·갱신 대기·실패는 데이터 문장과 별도 UI 상태로 표현한다.
- 새 계약이 확정되기 전까지 기존 API를 화면에 맞추기 위해 추가 해석하지 않는다.

## 5. 이후 설계해야 할 화면 상태

| 상태 | 의미 | 화면 처리 |
|---|---|---|
| `EMPTY` | 아직 projection 없음 | 우측 빈 영역 유지 |
| `LOADING` | 새 projection 생성 중 | 패널 영역만 로딩 표시 |
| `READY` | 최신 LLM 문장 사용 가능 | View Model 문장 표시 |
| `STALE` | 사건 revision보다 오래됨 | 갱신 대기 표시 |
| `FAILED` | provider/API 실패 | 실패 안내와 재시도만 표시 |
