## 1. 결론

사건 맥락을 ‘AI 결과 문자열 목록’에서 ‘은행 직원이 편집할 수 있는 현재 사건 정리’로 개선한다. AI는 최신 Shared Case의 근거를 바탕으로 초안을 갱신하고, 담당자는 수정·추가·제외·완료를 통제한다. 과거 이력은 별도 기록으로 남기고 현재 요약에는 현재 판단에 필요한 내용만 표시한다.

기존 context_revision 계획에 **직원 수정 보존, 삭제 항목 재생성 방지, 항목별 식별자**를 함께 포함해야 한다. 버전 관리만 먼저 구현하면 최신 AI 결과가 직원의 수정본을 덮는 문제가 남는다.

## 2. 실제 원인과 확인 근거

| 현상 | 코드에서 확인한 원인 | 개선 방향 |
|---|---|---|
| 요약이 길게 이어 붙음 | `case_snapshot_adapter.py::_synthesize_summary`가 초기 요약·고객 상태·업무·다음 확인을 문자열로 연결하고 600자로 자름 | 최신 근거를 입력으로 구조화된 요약을 재작성하고 항목별 렌더링 |
| 질문이 ‘조치 진행 중’ 문장에 섞임 | 실제 action_type은 `AI_CHECKLIST:P0:...`인데 제외 조건이 `note.startswith('AI_CHECKLIST:')`를 검사함 | 체크리스트를 행동 사실로 취급하지 않고 정확한 종류로 분리 |
| AI 요약으로 보이나 매번 LLM 재작성은 아님 | `CaseSnapshotAiAdapter`는 동기 `build_brief()`와 규칙 합성을 사용. 별도 비동기 LLM build 경로의 존재만으로 현재 화면 연동을 판단할 수 없음 | LLM 생성 결과와 규칙 기반 표시를 명확히 구분하고 마지막 성공 결과 저장 |
| ‘모든 Shared Case 정보 종합’에 입력 누락 | `get_case_support_snapshot`은 diagnosis/facts/questions/verifications/actions를 전달하며 메시지 자체·참여자/메인 담당자 정보가 빠져 있음 | 은행 직원에게 허용된 최신 대화·담당자 정보를 snapshot 계약에 포함하고 출처/가시성 유지 |
| Impersonation / Action Request 신호 노출 | `signal_projection.py::_label`의 미등록 코드 fallback이 영문 family를 title-case로 만들어 evidence에 저장 | 구조화 피처와 별도 한국어 display_text·근거를 함께 보존 |
| personal_info_shared 노출 | `repository.py::normalize_target_field`에 해당 별칭이 없고 라벨 fallback이 코드로 돌아감 | 필드 별칭·한국어 업무명 사전 통일 및 기존 데이터 호환 처리 |
| 사건 맥락 수정·삭제가 없음 | `CaseContextPanel.tsx`의 요약·신호·주장·요구는 문자열/배열 표시. 판단 추가와 완료 토글만 있음 | 안정적인 항목 ID와 CRUD 계약부터 추가 |
| 체크리스트 내용이 변화에 뒤처짐 | `main.py::sync_ai_checklist_items`가 필드가 존재하면 계속 건너뛰므로 질문 대기→답변 수신 변화가 기존 문구에 반영되지 않음 | 항목 정체성·작업 목적·출처 버전을 기준으로 갱신/재검토 |
| 체크리스트 연필·X가 없음 | `PublicUpdateActionRequest`는 상태 변경만 지원. 행 전체 label과 전역 busy 사용 | 내용 수정·논리 삭제 API 및 항목별 작업 상태 |
| 사건 맥락이 좁음 | `styles.css`의 case-room-grid는 `minmax(480px, 1fr) 320px`; 좁은 화면은 360px/92vw 서랍 | 채팅 최소 너비를 유지하는 제한된 리사이즈 |

## 3. 현재 사건 요약의 표현

권장 구성은 **사건 개요 / 피해·노출 / 핵심 미확인 / 다음 업무**의 최대 4개 항목이다. 각 항목은 한 문장 중심으로 작성한다. 중복 질답, 과거 상태 나열, 체크리스트 원문을 넣지 않는다. 긴 상세 근거는 펼쳐보기와 원래 기록 링크로 제공한다. 길이 제한은 검증 기준으로 쓰되 문장을 임의의 글자 위치에서 잘라 저장하지 않는다.

다음은 형식 예시이며 실제 Case에 없는 사실을 자동 추가하는 템플릿이 아니다.

| 구분 | 예시 |
|---|---|
| 사건 개요 | 검찰 수사관을 사칭해 범죄 연루를 주장하며 안전계좌 이체를 요구한 정황입니다. |
| 피해·노출 | 고객은 송금했다고 답변했으며, 송금 금액은 확인되지 않았습니다. |
| 핵심 미확인 | 인증정보 제공 여부는 고객이 확실히 기억하지 못하고 있습니다. |
| 다음 업무 | 송금 내역과 추가 이체 가능성을 확인합니다. |

고객 진술·AI 추정·담당자 확정·기관 검증 결과를 구별한다. ‘잘 모르겠어요’는 제공하지 않았다는 뜻도, 제공했다는 확정도 아니다. 직원 확정 이후 상충하는 답변이 들어오면 기존 사실을 조용히 바꾸지 않고 ‘상충 정보 검토’로 표시한다.

## 4. 자연어 신호와 저장 방식

- 내부 피처 코드는 분석·추적에 유지하고, 별도 display_text에 은행 직원이 읽을 한국어 문장을 저장한다.
- 예: 구체적인 근거가 있는 경우 `Impersonation 신호` → ‘상대방이 검찰 수사관이라고 주장했습니다.’
- 예: 이체 목적과 요구가 확인된 경우 `Action Request 신호` → ‘계좌 검증을 이유로 안전계좌 이체를 요구했습니다.’
- 세부 근거가 없으면 ‘기관 소속 사칭 가능성이 탐지됐으며, 주장 기관은 확인이 필요합니다.’ 정도로 제한한다. 한국어화 과정에서 기관·금액·행동을 지어내지 않는다.
- 신호, 상대방 주장, 요구 행동이 같은 문장을 세 번 반복하지 않도록 각 영역의 역할을 나눈다.
- 미등록 코드도 영어 fallback을 직원 화면에 노출하지 않는다. 안전한 한국어 표현과 내부 진단 기록을 사용한다.
- 원문 통화를 Shared Case에 저장하지 않는 기존 정책을 유지한다. 자연어 설명은 구조화 피처·저장된 고객 답변·확인 결과에서 생성한 파생 정보이며, 초기 통화 원문 저장을 다시 허용하는 의미가 아니다.

## 5. 은행 직원의 CRUD와 AI 갱신 권한

| 대상 | 직원 조작 | 저장 원칙 |
|---|---|---|
| 현재 사건 요약 | 항목별 수정, 항목 추가/제외, AI 초안 비교 | AI 원안과 직원 수정본을 분리; 빈 섹션도 추가로 복원 가능 |
| 신호·상대방 주장·요구·기타 | 항목 추가/수정/삭제 | 안정적인 ID·근거·변경 이력 유지 |
| 확인된 사실·기관 확인 결과 | 원래 사실/검증 편집 기능으로 연결 | 화면 설명 편집과 실제 사실 정정은 구분; 정정 이유·수정자 기록 |
| 담당자 판단·조치 | 추가/수정/완료/삭제·복원 | 기존 업무 ID에 연결하여 서로 다른 기록이 되지 않게 함 |

AI 원안, 직원 편집본, 현재 표시본을 분리한다. 직원 수정본은 AI가 자동 덮어쓰지 않는다. 새로운 근거로 AI 제안이 달라지면 ‘새 제안 검토’에서 비교 후 적용한다. ‘AI 자동 갱신으로 되돌리기’는 명시적 조작으로 제공한다.

X 삭제는 기본적으로 **현재 사건 맥락에서 제외**하는 논리 삭제다. 원래 대화·증거·기관 결과를 지우는 의미가 아니다. 삭제 목록과 실행 취소/복원 기능을 제공한다. 삭제 식별 정보(tombstone)를 유지해 같은 내용이 다음 AI 갱신 때 살아나지 않게 한다. 중요한 새 근거가 생겼을 때도 자동 복원하지 않고 재검토 제안을 한다.

직원 두 명의 동시 편집은 expected_version으로 충돌을 감지한다. 수정 중 도착한 갱신은 초안·커서·스크롤을 보존하고 저장 시 비교 안내한다. UI 권한뿐 아니라 서버에서 직원 권한을 확인해야 하며, 현재 실제 인증/RBAC의 완성도를 먼저 점검한다.

## 6. AI 추가 확인 체크리스트

행은 **업무 제목 / 현재 상태 / 필요 시 근거**와 `연필 · 체크 · X`를 제공한다. 예: ‘송금 금액 확인’ / ‘고객 답변 대기’. 고객 질문 원문과 기술 코드가 긴 업무 제목이 되지 않게 한다.

- 연필: 인라인 수정, 저장/취소. 한 항목 저장 중 다른 항목의 조작을 막지 않는다.
- 체크: 의미를 ‘완료 처리’로 명시한다. 사용자가 말한 ‘진행’은 별도 ‘진행 중’ 상태로 제공하여 시작과 완료를 구분한다.
- X: 현재 목록에서 삭제/제외. 완료와 삭제를 다른 상태로 기록한다.
- 완료 목록과 삭제 목록을 별도로 열어볼 수 있고 완료 해제·삭제 복원이 가능하다.
- 체크리스트 완료는 사실 확정, 고객 답변 대리 입력, 지급정지 실행을 의미하지 않는다.
- 이미 고객에게 보낸 질문은 은행 체크리스트 삭제만으로 취소되지 않는다. 발송 취소가 필요하면 별도 기능과 표시가 필요하다.
- 고객 답변이 들어오면 ‘답변 대기’가 끝나고 필요한 경우 ‘답변 검토’ 업무로 바뀐다. 완료한 과거 업무를 새 업무로 오인하지 않도록 목적과 근거 버전을 보존한다.
- 모든 아이콘에 tooltip·aria-label·키보드 조작을 제공한다. 터치에서도 버튼을 찾을 수 있게 하며 행 전체 label 안에 편집 버튼을 중첩하지 않는다.

## 7. 사건 맥락 너비 조절

데스크톱 기본 400px, 최소 320px를 초기 제안으로 삼는다. 최대 너비는 사건 영역의 가용 너비에서 채팅 최소 480px와 경계 너비를 제외한 값으로 제한한다. 숫자는 대표 화면 검증 후 확정한다.

패널 왼쪽 경계 드래그, 키보드 좌우 조절, 기본 너비 복원을 제공한다. 사용자·브라우저별로 저장하고 창 크기 변경 시 가용 범위로 재조정한다. 폭 조절은 사건 데이터 변경이 아니므로 context_revision 증가나 AI 호출을 유발하지 않는다. 좁은 화면에서는 리사이즈 대신 기존 서랍/전체보기 방식으로 전환한다.

## 8. 에이전트 관점별 검토와 통합 판단

- UX: 현재 요약은 3~4개 짧은 항목으로 읽게 하고, 각 항목의 근거와 편집 상태를 가까이 배치해야 함. 채팅 최소 너비·입력 포커스 보존이 필수.
- AI·데이터: 문자열을 다시 합치는 방식은 한계가 있음. 체크리스트 혼입 오류를 먼저 제거하고, 구조화 요약·한국어 설명을 별도 projection으로 저장해야 함.
- QA: 직원 편집 중 AI 갱신, 삭제 후 재생성, 동일 필드의 새 업무, 동시 편집 충돌이 핵심 검증 대상. 완료 체크와 사실 확정을 분리해야 함.
- 통합 판단: 데이터 항목 계약과 직원 권한·우선권 → revision/마지막 정상 결과 → 요약·자연어 생성 → CRUD/체크리스트 → 리사이즈 순으로 진행. 리사이즈는 의존성이 낮아 별도 작업 가능.

## 9. 기존 개선 사항과의 관계

분석 요청 추적, AI·DB 오류 분리, 생성 후 조회 실패 처리, 질문 UUID·동시성 보강, ML 실행 환경 정리는 이전 단계의 완료 항목이다. 이번 회의가 해당 코드를 재작업하거나 실제 LLM 사건 맥락 재생성이 이미 완료됐다고 보는 것은 아니다.

context_revision/마지막 성공 projection은 미구현 후속 항목이며 이번 CRUD 설계와 통합한다. 채팅 반영, 답변→피해 상태·체크리스트 반영, 중복 질문, E2E, 성능 검증은 이를 적용한 뒤 수행한다.
