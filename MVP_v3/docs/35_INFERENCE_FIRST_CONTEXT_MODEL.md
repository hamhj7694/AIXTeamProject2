# 추정·정황 중심 Case Context 운영 모델

상태: 데모 운영 기준선 — 확정/승격 개념 폐지
작성일: 2026-09-22

## 1. 목적

CSR의 현재 데모에서는 `미확정 → 확정`이라는 이분법과 승격 절차를 사용하지 않는다.
입력·분석·대화에서 생성되는 정보는 모두 **준사실에 가까운 추정·정황 정보**로 취급하고, 은행 직원은 이를 참고해 질문·확인·보호 조치를 바로 진행한다.

확정 기준과 승격 규칙은 현재 제품 계약에서 폐지하고, 향후 별도 설계에서 다시 결정한다. 기존 V2 Fact의 상태 필드는 API·데이터 호환을 위한 레거시 값으로만 보존한다.

## 2. 핵심 원칙

1. AI 분석 결과는 사실을 단정하지 않고 정황으로 표현한다.
2. 직원은 확정 버튼을 누르지 않아도 사건을 검토하고 대응 업무를 시작할 수 있다.
3. 고객 발언·AI 추출·직원 입력은 모두 출처를 보존한 분석 정보로 취급한다.
4. 분석 정보와 실제 업무 처리 결과를 섞지 않는다.
5. 고객에게 공개할 수 있는 정보와 은행 내부 참고 정보는 `visibility`로 분리한다.
6. 새로운 대화가 기존 분석과 충돌해도 AI가 기존 내용을 자동 삭제·확정 취소하지 않는다.
7. 새 구분 기준을 설계할 때까지 변경 이력과 근거 연결만 유지한다.

## 3. 사용자 화면 표현

화면에서 `미확정`, `확정 대기`, `승격`을 기본 흐름으로 사용하지 않는다. 현재 사용 중인 정황 중심 표현을 기준으로 한다.

권장 표현:

- 주요 정황
- 상대방 주장
- 상대방 요구
- 분석에서 확인된 내용
- 추가 확인이 필요한 내용
- 담당자 조치 현황
- 고객에게 확인할 내용

피해야 할 표현:

- AI가 확정한 사실
- 범죄가 확정됨
- 실제 송금이 확인됨 (은행 근거가 없는 경우)
- 보이스피싱범으로 확정
- 담당자가 확인하지 않아 사용할 수 없음

예시:

```text
주요 정황
- 상대방이 검찰 수사관이라고 주장함
- 안전계좌로 이체하라고 요구함
- 오늘 안에 처리하라고 재촉함

추가 확인이 필요한 내용
- 실제 송금 여부
- 요구받은 계좌의 실제 명의
- 상대방 주장의 사실 여부

담당자 조치 현황
- 고객에게 송금 여부 확인 요청
- 공식 기관 연락처를 통한 사칭 여부 확인 예정
```

## 4. 데이터 처리 흐름

```text
원문·채팅 입력
  → 구조화 분석(Atom·Relation·Feature)
  → 분석 정황 저장
  → Case Context·은행 AI·고객 공개 projection
  → 직원의 질문·확인·보호 조치
  → 새 메시지·확인 결과를 추가 정황으로 저장
```

초기 분석이나 채팅 추출 결과를 `CONFIRMED`로 자동 생성하지 않는다. 직원의 업무 행동도 곧바로 사실 확정으로 간주하지 않으며, 확인 결과가 필요하면 별도의 메시지·Verification·Action 기록으로 남긴다.

## 5. 최소 데이터 계약

초기 운영에서 모든 분석 정보는 다음 속성을 보존한다.

| 필드 | 의미 |
|---|---|
| `semantic_key` | 정보의 의미를 식별하는 안정적인 키 |
| `value` / `display_value` | 내부 구조화 값과 화면 표시값 |
| `source_kind` | AI 분석·고객 발언·직원 입력 등 출처 |
| `evidence_refs` | 메시지·이벤트·분석 lineage 근거 |
| `confidence` | 모델 또는 추출기의 참고 신뢰도. 사실 확정값이 아님 |
| `visibility` | 은행 내부·고객 공개 등 표시 경계 |
| `created_at` / `updated_at` | 생성·변경 시각 |
| `version` | 동시 수정 충돌 방지용 버전 |

`confidence`가 높아도 자동 확정하지 않는다. 신뢰도는 우선순위와 검토 대상을 정하는 참고값이다.

## 6. 업무 처리 규칙

직원은 다음 업무를 즉시 수행할 수 있다.

- 고객에게 추가 질문
- 기관 확인 업무 등록
- 지급정지·보호 조치 검토 기록
- 담당자 간 내부 소통
- 송금 기록 조회 또는 데모 기록 입력
- AI에게 최신 Case 정황 요약 요청

단, 업무가 완료되었다는 기록과 분석 정황은 별개다. 예를 들어 “기관 확인 요청을 등록함”은 업무 기록이지 “기관 사칭이 사실로 확정됨”을 의미하지 않는다.

## 7. 고객 공개 안전 경계

확정 상태를 사용자 흐름에서 제거하더라도 고객 화면에 모든 정황을 그대로 공개하지 않는다.

- `BANK_INTERNAL` 정보는 은행 화면에만 표시
- 고객에게 공개할 수 있는 정보만 `CUSTOMER_SHARED` projection으로 전달
- AI·직원 내부 판단, 민감한 기관 확인 메모, 내부 위험 점수는 고객에게 전달하지 않음
- 고객 공개 문장은 “확인 중”, “추가 확인이 필요합니다”, “담당자가 확인하고 있습니다”처럼 단정하지 않음

## 8. 기존 V2 Fact와의 호환(레거시)

현재 `case_context_facts_v2`의 상태 필드는 즉시 삭제하지 않는다. 이는 현재 제품의 의미 체계가 아니라 기존 데이터·API 호환을 위한 레거시 값이다. 새 화면과 업무 흐름에서는 상태를 판단 기준으로 사용하지 않는다.

- 출처·근거·변경 이력 보존
- 고객 공개 projection 판정
- 기존 API와 데이터 호환
- 추후 담당자 확인 기능을 추가할 때의 확장 지점

새 상태명·구분 기준·승격 규칙은 현재 문서에서 미리 정의하지 않는다. 관련 요구가 정리된 뒤 별도의 제품 계약으로 작성한다.

## 9. 충돌 처리

새 채팅이나 직원 입력이 기존 정보와 다를 때의 기본 동작은 다음과 같다.

1. 기존 분석 정보를 자동 삭제하지 않는다.
2. 새 내용을 별도 분석 정황으로 저장한다.
3. 화면에는 “기존 내용과 다른 정보가 입력됨” 또는 “추가 확인 필요”를 표시한다.
4. 직원이 질문·기관 확인·업무 기록으로 후속 대응한다.
5. 기존 정보의 변경·대체가 필요하면 이력과 근거를 남기되, 현재 데모에서는 확정 상태 전환을 수행하지 않는다.

## 10. 이 모델에서 하지 않는 것

- AI 결과만으로 실제 송금·피해·사칭을 확정하지 않음
- 직원이 채팅으로 확신을 표현했다는 이유만으로 자동 확정하지 않음
- confidence 점수만으로 공개·차단·지급정지 결정을 자동 실행하지 않음
- 기존 정황을 새 AI 결과로 자동 덮어쓰지 않음
- `cases.actual_loss_amount_krw`를 분석 금액의 자동 합계로 만들지 않음

## 11. 이후 구분 기준을 설계할 때의 검토 항목

- 사실 종류별 최소 근거 정책(거래·기관 확인·고객 진술 등)
- 담당자 역할별 확인 권한
- `STAFF_CHECKED`와 법적·공식 확인의 구분
- 고객 공개 승인과 내부 확인의 분리
- `UNCONFIRM`, `INVALIDATE`, `SUPERSEDE`의 차이
- 기존 정황과 새 확인 결과의 충돌 해결
- 감사 이력·확인자·확인 시각·근거 필수값

## 12. 완료 기준

- [ ] 직원이 상태 승격 없이 분석 정황을 보고 질문·조치를 시작할 수 있다.
- [ ] AI·고객·직원 입력의 출처와 근거가 보존된다.
- [ ] 화면 문구가 사실 단정 대신 정황·확인 필요 표현을 사용한다.
- [ ] 고객 화면에는 허용된 정황만 projection된다.
- [ ] 기존 `case_context_facts_v2` 이력과 API 호환이 유지된다.
- [ ] 새 정보가 기존 내용을 자동 삭제·덮어쓰지 않는다.
- [x] 확정·승격 기능은 현재 제품 계약에서 폐지하고 필수 경로로 사용하지 않는다.
