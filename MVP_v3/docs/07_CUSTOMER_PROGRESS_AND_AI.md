# 고객 공개 처리 상태와 AI 연동

## 해결한 문제

피해구제 안내의 마지막 선택 단계로 이전 절차까지 완료 처리하던 UI 계산을 제거했다. 사건의 CLOSED 상태, 안내 열람, 고객 진술, 질문 카드 응답, 일반 업무 체크 완료는 지급정지·신고·피해구제 접수 완료 근거로 사용하지 않는다.

## 사용 흐름

1. 고객의 현재 진행 상황에는 절차별 확인 상태, 공개 결과, 지금 할 일, 확인 근거와 시각이 표시된다.
2. 고객이 `담당자에게 확인 요청`을 누르면 요청을 DB에 저장한다. 이미 대기 중인 동일 절차 요청은 중복 저장하지 않는다. 이 요청은 공식 신청 접수가 아니다.
3. 은행 화면의 사건 맥락 상단 `고객에게 공유할 처리 결과`에서 요청을 확인하고 `결과 기록`을 연다.
4. 담당자는 상태, 고객에게 공개할 결과, 고객이 할 일, 근거/접수번호, 확인 시각을 입력한다. 제출 확인 및 완료 확인은 근거와 시각 없이 저장할 수 없다.
5. 저장하면 고객 확인 요청 대기를 해제한다. 은행·고객 Bundle과 고객 AI가 같은 공개 상태를 사용한다. 신청 접수 확인은 환급 완료와 구분한다.

상태: 확인되지 않음 / 담당자 확인·처리 중 / 제출 확인·접수 결과 대기 / 담당자 완료 확인 / 해당 없음.
절차: 추가 송금·접촉 중단 / 증빙 확보 / 은행 지급정지 / 기관 신고 접수 / 피해구제 신청 접수. 각각 독립적이며 순서대로 모두 완료된다고 가정하지 않는다.

## 데이터와 API

- GET `/api/cases/{case_id}/customer-progress`
- PUT `/api/cases/{case_id}/customer-progress/{step}`: 담당자 공개 결과 기록, expected_revision 검사
- POST `/api/cases/{case_id}/customer-progress/{step}/confirmation-request`: 고객 확인 요청
- Bundle의 `customer_progress`: 은행과 고객에 동일한 공개 데이터 전달
- AI 계약의 `customer_progress`, `published_verification_results`: 고객 공개 결과만 전달

기존 actions 테이블에 `CUSTOMER_PROGRESS:{step}` 전용 타입과 검증된 JSON 스냅샷을 append-only로 저장한다. 이번 변경은 별도 DB 마이그레이션이 필요 없다. 이력은 남기고 절차별 가장 높은 revision을 사용한다. 일반 actions API/타임라인에는 내부 JSON을 노출하지 않는다. AI 사건 맥락에는 최신 기록만 자연어화하여 제공한다.

MySQL은 Case 행을 FOR UPDATE로 잠근 동일 트랜잭션에서 현재 상태 조회, 중복/수정 버전 검사, 기록과 이벤트 저장을 처리한다. 기존 actions 변경 트리거로 context_revision도 갱신된다. 일반 actions API에서 이 전용 타입을 생성하거나 체크 완료로 변경하는 것은 차단한다.

고객 화면은 기존 4초, 은행 화면은 5초 갱신 주기에 반영된다. 저장한 본인 화면에는 응답을 즉시 반영한다. 편집 중 폼은 주기적 조회 결과로 덮어쓰지 않으며 동시 수정 시 409를 반환한다. 충돌 시 폼을 취소하고 최신 항목의 `결과 기록`을 다시 열어 입력한다.

## AI 동작

고객 AI는 호출 시 공개 처리 상태, 최근 고객 대화, 고객 질문 답변, 고객 공개 첨부 파일명, 고객 공개로 확정된 기관 결과를 읽는다. 은행 내부 대화나 비공개 검증 결과는 전달하지 않는다. 공개 처리 상태를 과거 AI 답변보다 우선하도록 지시한다. 담당자 확인 요청이 이미 저장됐는지 설명하고, 요청이 없을 때 화면의 요청 버튼을 안내한다.

AI 응답 호출에 외부 금융 업무 실행 도구는 추가하지 않았다. 공식 접수·전달을 실행했다고 말하지 않도록 지시한다. 실제 외부 시스템 연결 전까지 완료의 출처는 직원의 확인 기록이다. 기존 MVP API와 같은 인증 구조를 사용하며 운영 배포의 직원 인증·인가 체계 구축을 대체하지 않는다.

## 검증 및 적용

- 백엔드: 고객 진행 상태, SQL 트랜잭션, 동시 요청, 충돌, 공개 정보 필터, Bundle 일치, AI 프롬프트 전달 및 기존 관련 회귀 테스트
- 프론트: `node scripts/test-customer-progress.cjs`로 실제 컴포넌트 렌더링의 오완료·누락 상태·중복 요청 노출 방지 검사
- `npm.cmd run build` (TypeScript 포함)

실제 MySQL에 대한 신규 기록 저장과 실제 LLM의 답변 품질은 이번 자동 검사에서 실행하지 않았다. SQL 저장 경로는 모의 커넥션으로 트랜잭션을 검사했으며, LLM은 모의 응답으로 실제 전달 입력을 검사했다. 실행 중인 서비스에 반영하려면 General API, AI API를 함께 재시작하고 프론트 최신 코드를 적용한다.
