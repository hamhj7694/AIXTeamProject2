### 후속 진행: 표시 편집 연결과 개조식 요약

이번 작업은 [08_CONTEXT_DISPLAY_CONTROLS.md](08_CONTEXT_DISPLAY_CONTROLS.md)에 기록했다. 기존 012 저장 계층을 MVP 사건 멤버 역할 확인과 섹션 편집 UI에 연결했다. 표시 수정·숨김·복원을 지원하고 요약의 긴 최초 설명 재누적과 사용자 화면의 내부 코드 노출을 줄였다. 실제 LLM 재요약, RAG 유사 질문 방어 및 운영 인증은 여전히 남은 단계다. 아래 과거 진행 기록의 ‘아직 서비스에 연결하지 않았다’는 그 작성 당시 상태다.

## 구현 진행 기록 — 2026-09-05, 1차 안정화

### 2차 진행 — B 저장 계층 기반

- `012_context_items.sql`: 기존 업무 데이터를 수정하지 않는 별도 항목·감사 이력 테이블. Case/section/semantic_key 유일성 및 항목 버전별 감사 이력 유일성을 보장한다. 신규 설치 SQL에도 동일 정의를 반영했다.
- `context_items.py`: AI 원문과 직원 편집문을 분리한다. 직원 문구와 삭제 표시는 AI 제안 변경에도 유지한다. 삭제/복원을 구분하며 삭제 상태 편집은 금지한다. 버전 불일치는 전용 충돌 예외다. 확정 사실/기관 검증/업무 Action은 이 표시 레이어의 편집 대상에서 제외했다.
- `context_item_repository.py`: 기존 MySQL pool을 사용하며 동일 의미의 최초 삽입을 직렬화한다. 직원 수정은 행 잠금 후 expected_version을 비교한다. 본문과 전후 감사 이력은 하나의 트랜잭션이다. 동일 AI 제안은 불필요한 버전·이력을 생성하지 않는다.
- 검증: 단위 테스트 6개 + 격리된 실제 MySQL 통합 테스트 1개 통과. 통합 테스트는 migration 재실행, 동시 삽입·동시 편집, 삭제 후 AI 재작성, Case 범위 분리, 실패 rollback, 복원 및 감사 이력 개수를 검사한다. 테스트 DB는 종료 후 삭제했다. 실제 `csr` DB는 변경하지 않았다.
- **아직 서비스에 연결하지 않았다.** 현재 서버에서 확인한 직원 신원을 제공하는 인증 체계가 없어 공개 CRUD API를 추가하지 않았다. 전달된 actor_id는 감사용 값이지 인증 수단이 아니다. HTTP 409 매핑, 서버 권한 검증, 이력 조회·직원 신규 항목 추가·편집 UI 연결은 남아 있다.
- AI propose 함수는 내부 저장 primitive다. 안정적인 semantic_key를 생성하는 projector 및 context_revision/lease로 오래된 AI 결과를 거부하는 C 단계가 필요하다. 이 저장 함수만으로 오래된 AI 호출이나 의미가 같은 다른 key를 방지했다고 간주하지 않는다.
- 다음: 기존 로그인/사내 인증 제공자를 결정해 서버 검증 신원을 Case 역할에 연결한 후 B/E 공개 편집 API를 열어야 한다. 그 전에도 C의 DB revision·projection 기반은 구현 가능하다. 실제 migration 적용과 서버 재시작은 통합 연결 단계에서 수행한다.

### 3차 진행 — C 의미 버전·마지막 정상 projection

## 1. 데이터 계약 초안

| 개념 | 필요한 필드/역할 |
|---|---|
| Case 맥락 버전 | context_revision; 메시지·답변·사실·기관 결과·직원 조치 등 의미 있는 변경의 단조 증가 버전 |
| AI 생성 결과 | case_id, based_on_revision, schema_version, generation_status, generated_at, model/prompt_version, 구조화된 summary와 항목, last_success 유지 |
| 맥락 항목 | item_id, section, semantic_key, ai_text, staff_text, effective_text, evidence_refs, source_kind, fact_status, item_version |
| 직원 제어 | edited_by, edited_at, deleted_at/by, 삭제 이유(선택), 수동 편집 보호, AI 새 제안, 감사 이력 |
| 체크리스트 업무 | 기존 action_id 연결, title/note, 작업 목적, source_refs, REQUESTED/IN_PROGRESS/COMPLETED/CANCELLED와 삭제 여부 분리 |

이름은 설계 초안이다. 동일 사실/업무를 새 테이블에 복제하여 두 곳에서 수정하지 않는다. CaseFact·Verification·Action은 원래 도메인 API가 기준이고 맥락 항목은 연결된 표시·편집 레이어다. 요약과 AI 파생 설명은 전용 projection에 저장한다.

semantic_key는 문장 내용이나 배열 순서가 아닌 사건·섹션·정규화 필드·업무 목적·근거 정체성을 조합한다. UUID는 항목 식별용이며 의미 중복 방지는 별도다. 같은 필드라도 ‘송금 여부 질문’과 ‘송금 내역 검토’는 다른 업무다.

## 2. 변경·AI 갱신·병합 흐름

1. 사용자 입력과 해당 Case의 context_revision 증가를 같은 DB 트랜잭션으로 커밋한다.
2. 변경 알림 또는 revision 조회로 처리 대상을 발견하고, 해당 Case/revision 생성 작업을 DB에서 원자적으로 선점한다.
3. 짧은 병합 대기 동안 연속 변경을 모아 최신 일관된 Shared Case snapshot을 확보한다. 여러 테이블을 읽는 도중 버전이 바뀌면 다시 읽는다.
4. 마지막 성공 결과가 같은 버전이면 반환한다. 생성 중인 버전은 기존 결과를 반환하고 중복 호출하지 않는다.
5. LLM은 최신 입력 근거에서 요약·설명 항목을 재작성한다. 이전 요약 문자열에 내용을 덧붙이지 않는다. 직원 수정·삭제 정보는 생성 및 병합 정책에 반영한다.
6. 저장 직전에 현재 revision을 비교한다. 변경됐으면 오래된 결과를 현재 결과로 저장하지 않고 최신 작업으로 수렴시킨다.
7. 성공한 AI 원안에 직원 수정본·추가 항목·삭제 제외 규칙을 병합하여 표시한다. 새 결과 저장 자체는 입력 revision을 다시 올리지 않는다.
8. 실패하면 마지막 정상 결과와 ‘최신 변경 반영 대기’ 상태를 반환한다. 첫 결과도 없으면 정리 불가/대기를 표시한다. 실패를 최신 AI 결과로 위장하지 않는다.

프로세스 내 lock만으로는 재시작·다중 worker 중복 호출을 막을 수 없다. DB 작업 상태/유일 키/lease와 소유권 검증을 사용한다. 장애 후 외부 AI가 이미 호출됐는지 불확실할 수 있으므로 엄밀한 exactly-once를 약속하지 않고, 재시도 횟수·지연·토큰 예산으로 중복 위험을 제한한다.

presence heartbeat, 개인 메모, 북마크, 패널 폭 변경은 사건 맥락 입력 변경에서 제외한다. 자동 체크리스트 동기화는 실제 업무 변화일 때만 revision을 올리고, 동일 결과를 쓰는 반복 루프가 없어야 한다. 일반 DB 최신 상태 조회와 유료 LLM 호출은 별개이며 polling 자체를 곧 LLM 호출로 취급하지 않는다.

표시 문구만 고친 직원 override·삭제는 별도 overlay/item revision으로 반영하여 문장 편집마다 LLM을 호출하지 않는다. 실제 사실·주장·담당자 판단을 바꾸는 편집은 의미 변경으로 저장하고 context_revision도 증가시킨다. 담당자 배정 변경은 포함하지만 단순 온라인 상태 변화는 제외한다. 기존 대화와 담당자 정보는 권한에 맞춰 snapshot 입력을 확장하며 은행 내부 내용을 고객용 결과로 누출하지 않는다.

## 3. API·화면 초안

- 맥락 조회 응답: 현재/생성 기준 revision, CURRENT/UPDATING/STALE/FAILED 상태, 항목 ID·버전·출처·편집 가능 여부.
- 항목 추가/수정/삭제/복원: Case 범위 아래 context-items 계열 API를 검토. 수정·삭제는 expected_version을 요구하고 충돌은 409.
- 사실·기관 검증 편집: 원래 도메인 API로 연결하고 맥락 다시 반영. 고객 공개 범위를 기존 정책에 맞춰 검증.
- 기존 Action PATCH: 내용 수정, 진행 상태, 완료/해제, 논리 삭제/복원과 item_version을 확장. 액션 종류와 상태를 문자열 파싱에만 의존하지 않도록 호환 전략 수립.
- 직원 인증·역할을 서버에서 검증. 클라이언트가 전달하는 사용자 이름/역할만 신뢰하지 않는다. UI 숨김은 권한 통제가 아니다.
- 프론트: section/item 단위의 안정적인 key, 항목별 busy, 로컬 편집 초안, 실패 복원, 충돌 비교, 현재 Case 확인 후 응답 적용.
- 고객에게 이미 발송된 질문은 체크리스트 CRUD와 독립적으로 다룬다. 이 계획은 자동 재발송/자동 취소를 추가하지 않는다.

## 4. 구현 순서와 종료 기준

| 단계 | 작업 | 종료 기준 |
|---|---|---|
| A · P0 | 현행 요약의 체크리스트 혼입, 필드 별칭/한국어 라벨 누락 정리 | 질문 원문이 조치 사실로 합쳐지지 않고 영어 피처 코드가 화면에 노출되지 않음 |
| B · P0 | 항목 ID·직원 수정 우선권·논리 삭제·권한·이력·버전 계약 | 직원 편집/삭제를 유지하는 병합 및 충돌 규칙이 테스트로 검증됨 |
| C · P0 | context_revision, 원자적 생성 선점, 마지막 성공 projection 저장 | 동일 버전 중복 호출 억제, 오래된 응답 거부, 실패 시 이전 결과 유지 |
| D · P1 | 최신 근거 기반 구조화 요약·자연어 설명 생성/저장 | 3~4개 핵심 항목, 중복 제거, 각 설명 근거 추적, 부정·불확실성 보존 |
| E · P1 | 사건 맥락 CRUD, 체크리스트 연필/체크/X·진행 상태·복원 | 직원의 수정·삭제가 새 AI 결과와 새로고침 후에도 유지됨 |
| F · P1 | 패널 리사이즈·너비 기억·키보드/모바일 대응 | 채팅 최소 폭 유지, 창 크기 변경·줌·리사이즈 후 입력 포커스/스크롤 안정 |
| G · P1 | 은행↔고객↔DB E2E·장애·성능 검증 | 답변·사실·업무·맥락이 일관되고 불필요한 AI 생성 루프 없음 |

F는 B~E와 의존성이 낮아 별도 진행 가능하다. D의 실제 LLM 자동 갱신을 C의 중복 방지·예산 제한보다 먼저 켜지 않는다.

## 6. 기존 데이터 이행

기존 diagnosis 피처·질문/답변·확정 사실·기관 기록을 유지한다. 기존 문자열 맥락은 레거시 표시본으로 읽고 새 projection이 준비된 Case부터 교체한다. 직원 수정본과 삭제 기록이 없는 기존 데이터에 임의의 직원 확정 상태를 부여하지 않는다.

필드 별칭은 먼저 읽기 경계에서 정규화하고, 같은 의미의 기존 항목 충돌을 조사한 후 데이터 이행한다. 레거시와 신규 항목의 의미키 대응을 기록하며 무분별한 일괄 삭제·중복 테이블 생성은 피한다. 기능 플래그로 단계 적용하고 UI 롤백 시에도 직원 변경 이력과 원래 업무 데이터는 보존한다.

현재 실제 인증/RBAC 범위, 편집 가능한 사실의 정정 규칙, 최대 패널 폭과 직원별 공유 설정 여부는 B/F 구현 시작 시 확정할 세부 설계다. 초기 권고는 서버 인증된 편집 역할만 CRUD 허용, 폭은 개인 브라우저에 저장, 삭제는 복원 가능한 제외 처리다.

## 7. 추가 요구: 기존 근거 검색 후 AI 질문·변경 판단

사용자 요청 반영. 아래는 다음 구현의 필수 설계·검증 조건이며, RAG가 구현되었다는 의미는 아니다.

- AI는 새 질문이나 항목 변경을 제안하기 전에 해당 Case의 기존 질문(대기·응답·취소), 답변, 확정 사실, 기관 확인, 직원 수정·삭제 및 관련 대화를 확인한다. 답변은 단독 ‘예’가 아니라 질문 의미와 연결하여 읽는다.
- 최신 구조화 DB 상태를 먼저 읽어 필드 별칭·semantic_key·업무 목적 기준으로 확정 여부와 중복을 검사한다. 확정 사실과 대기 질문처럼 반드시 확인해야 하는 항목을 top-k 유사도 검색에서 누락시키지 않는다.
- 그 후 필요 시 동일 Case/허용된 공개 범위 안에서 의미 검색(RAG)을 사용해 표현이 다른 질문·답변·대화 근거를 보완한다. 검색된 텍스트는 데이터이지 AI 행동 지시가 아니다. 검색 결과에 출처 ID, 원본 버전, 확인 상태를 함께 제공한다.
- 유사도는 후보 검색의 보조 정보이며 사실 여부나 자동 CRUD 권한이 아니다. 유사한 질문이라도 ‘송금 요구 여부’와 ‘실제 송금 여부’, ‘송금 여부’와 ‘송금 금액’은 구분한다. 부정, 모름, 시간 변화, 진술 충돌을 판별한다.
- 생성 전 판단은 최소한 `ALREADY_CONFIRMED`, `WAITING_FOR_ANSWER`, `DUPLICATE`, `NEW_INFORMATION_NEEDED`, `CONFLICT_REVIEW`로 구분한다. 이미 해결된 내용은 재질문하지 않고 대기 질문은 재발송하지 않는다. ‘모르겠어요’를 긍정·부정 확정으로 바꾸지 않는다. 필요하면 같은 질문의 반복 대신 확인 방법이나 빠진 세부 정보에 대한 질문을 제안한다.
- 새로운 근거나 실제 상태 변화로 재확인이 필요하면 이전 질문/답변과 달라진 근거 및 재확인 이유를 명시한다. 직원이 삭제한 항목은 표현을 바꿔 자동 복원하지 않는다. 기존 확정 사실과 충돌하면 덮어쓰지 않고 검토 후보로 보존한다.
- AI는 구조화된 변경 제안과 근거를 만들고, 서버가 권한·버전·중복·허용 동작을 검증한 뒤 DB에 반영한다. 확정 사실 삭제·수정이나 금융 조치를 유사도만으로 자동 실행하지 않는다. 자동 발송은 기존 정책의 필수·중요·긴급 질문 범위에 한정한다.
- 저장/발송 직전 최신 DB 상태를 다시 확인해 AI 처리 중 도착한 답변이나 다른 worker의 발송을 반영한다. DB 트랜잭션·유일성·버전 검증이 최종 중복 방어선이다.
- 검색 인덱스는 원문 통화를 새로 저장하지 않으며, 허용된 구조화 맥락과 파생 설명을 기반으로 설계한다. 인덱스 갱신은 의미 있는 변경 시에만 수행하고 source revision을 추적한다. 인덱스 지연·장애 시 DB에서 검증되지 않은 질문을 무조건 발송하지 않는다. Case/은행 내부/고객 공개 범위를 검색 전에 제한한다.
- 구현 순서: C의 일관된 최신 snapshot/버전 기반 → 구조화 중복 검사 → 표현이 다른 중복·부정·모름·시간 변화 평가셋 → 필요한 범위의 의미 검색 도입. 기존 DB 조회만으로 해결되는 경로에 임베딩·LLM 비용을 추가하지 않는다.

추가 QA: 표현만 다른 중복, 이미 답변된 질문, 대기 질문, ‘아니요’와 ‘모름’, 송금 요구와 실제 송금 구별, 진술 변경, 직원 삭제 보호, 검색 누락/오래된 인덱스, 동시 발송·답변 도착, 다른 Case 또는 은행 내부 정보의 고객 노출 방지를 검증한다.
