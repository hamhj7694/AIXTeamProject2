# 우측 패널 가이드 액션 라우팅 설계

## 목적

AI가 분석한 사건 정황에 따라 우측 패널의 가이드 항목에 필요한 기능을 연결한다.
가이드 제목은 평상시 텍스트로 표시하고, 실행 가능한 기능이 연결된 경우에만 제목을 클릭 가능한 액션으로 표시한다.

AI가 직접 프론트엔드 함수를 호출하지 않고, 구조화된 추천과 허용된 액션 의미만 반환하도록 한다.
프론트엔드는 허용 목록을 검증한 뒤 기존 화면 기능을 열고, 실제 등록·상태 변경은 담당자의 확인을 거쳐 기존 API로 처리한다.

## 기본 흐름

```text
원문·채팅 입력
→ 구조화 분석
→ 확인 필요 항목·대응 가이드 생성
→ action_key 부여
→ 프론트엔드 허용 목록 검증
→ 연결된 기능 열기/닫기
```

## 액션 키 계약

| action_key | 사용 조건 | 연결 기능 | 현재 상태 |
|---|---|---|---|
| `CUSTOMER_QUESTION` | 고객에게 추가 확인이 필요한 경우 | 고객 질문창 | 구현됨 |
| `TRANSACTION_LOOKUP` | 실제 송금·이체 여부 확인이 필요한 경우 | 송금 기록 조회 | 구현됨 |
| `OFFICIAL_VERIFICATION` | 기관·전화번호·공식 여부 확인이 필요한 경우 | 기관 확인창 | 구현됨 |
| `RESPONSE_ACTION` | 지급정지·연락 차단·신고 안내 등 대응 절차가 필요한 경우 | 대응 조치창 | 구현됨 |
| `NONE` | 안내만 필요하고 즉시 실행할 기능이 없는 경우 | 일반 텍스트 | 구현됨 |

## 가이드 액션 예시

`action_key`는 프론트엔드 가이드 라우팅에서 사용하는 허용 키다. AI는 이 의미를 참고한 구조화 추천을 반환할 수 있지만, 프론트엔드 함수를 직접 호출하지 않는다.

```json
{
  "title": "실제 송금 여부 확인",
  "description": "고객의 실제 이체 여부를 확인해야 합니다.",
  "stage": "recommended",
  "action_key": "TRANSACTION_LOOKUP",
  "reason_codes": ["TRANSFER_REQUEST", "TRANSFER_STATUS_UNKNOWN"]
}
```

질문이 필요한 경우:

```json
{
  "title": "인증정보 노출 여부 확인",
  "description": "인증번호·비밀번호 제공 여부를 고객에게 확인해야 합니다.",
  "action_key": "CUSTOMER_QUESTION",
  "reason_codes": ["CREDENTIAL_REQUEST", "EXPOSURE_UNKNOWN"]
}
```

## 프론트엔드 안전 규칙

1. `action_key`는 허용 목록에 있는 값만 처리한다.
2. 알 수 없는 값은 `NONE`으로 강등하고 일반 가이드 텍스트로 표시한다.
3. AI가 전달한 제목·설명은 표시용으로만 사용한다.
4. 액션 실행 권한과 실제 상태 변경은 프론트엔드·백엔드의 기존 권한 검사를 따른다.
5. 같은 액션 제목을 다시 클릭하면 연결된 창·카드를 닫는다.
6. 액션이 현재 Case 상태와 맞지 않으면 비활성 또는 일반 텍스트로 표시한다.

## 기능별 연결 기준

### 고객 질문

다음 정황이면 `CUSTOMER_QUESTION`을 부여한다.

- 고객의 송금 여부가 불명확함
- 인증정보·개인정보 노출 여부가 불명확함
- 상대방과 고객의 관계 또는 실제 행동 확인이 필요함

### 송금 기록 조회

다음 정황이면 `TRANSACTION_LOOKUP`을 부여한다.

- 송금·이체 요구가 있음
- 요구 금액은 있으나 실제 이체 여부가 불명확함
- 고객이 송금했다고 진술했으나 거래 기록 확인이 필요함

### 기관 확인

다음 정황이면 `OFFICIAL_VERIFICATION`을 부여한다.

- 검찰·경찰·은행 등 기관 사칭 주장이 있음
- 전화번호·소속·직책의 공식 여부 확인이 필요함
- AI가 기관 확인 필요성을 `reason_codes`와 함께 제안함

### 대응 조치

다음 정황이면 `RESPONSE_ACTION`을 부여한다.

- 지급정지·계좌 보호 등 즉시 조치 검토가 필요함
- 고객에게 신고·차단·안전 안내를 제공해야 함
- 담당자 업무·Task·Decision 등록이 필요함

## AI 판단과 직원 판단의 경계

- AI는 “어떤 확인 또는 조치가 필요한지”를 추천한다.
- AI 추천만으로 사실을 확정하거나 금융 조치를 실행하지 않는다.
- 기관 확인과 대응 조치는 신규 기능 구현 후에도 직원 확인·승인을 거쳐 실행한다.
- 근거가 부족하면 `NONE`으로 표시하고 가이드 설명에 추가 확인 필요를 남긴다.

## 구현 상태와 남은 작업

### 완료된 범위

- 기존 `CUSTOMER_QUESTION`, `TRANSACTION_LOOKUP`을 action_key 기반으로 정리
- AI·결정론적 가이드 모두 동일한 허용 목록 사용
- 제목 클릭 시 열기·닫기 토글 보장
- `OFFICIAL_VERIFICATION`은 기관 확인 보드에서 기존 Verification API와 발송 시뮬레이션 기록으로 연결
- `RESPONSE_ACTION`은 대응 조치 체크리스트에서 기존 Action API로 상태를 갱신
- `BANK_ACTION` AI 카드의 `suggested_actions`와 `VERIFICATION_REQUEST` AI 카드의 `verification_messages`를 계약에 반영
- `right-panel-guide-form`의 `AI 추천`은 `BANK_ACTION` 카드에서 초안을 받아 직원 검토 후 가이드로 추가

### 남은 작업

- AI 추천의 `action_key`·`reason_codes`를 우측 가이드 항목 자체에 영속화
- 직원이 만든 가이드의 배정·수행·완료 상태를 서버 Case 업무 리소스와 동기화
- 기관 확인과 대응 조치의 권한·감사 로그를 실제 운영 정책에 맞게 세분화

### 후속 고도화

- AI 추천의 `reason_codes`, 근거 Atom/Relation, 추천 우선순위 표시
- 액션 실행 결과를 Case 가이드 상태와 동기화
- AI 추천과 직원이 실제 수행한 조치를 구분해 저장

## 현재 범위

- DB 스키마 변경 없음
- AI가 프론트엔드 함수를 직접 호출하지 않음
- 기존 송금 기록 조회·고객 질문창을 먼저 action_key 방식으로 통합
- 기관 확인·대응 조치 기능은 기존 Verification·Action API와 연결된 상태이며, 가이드 자체의 서버 영속화는 후속 작업이다.

## GPT 제안 대비 현재 우측 패널 검토 (2026-09-28)

### 결론

GPT 제안의 핵심 방향인 “Chat은 수행, 우측 패널은 현재 상태와 사건 아카이브”는 현재 제품 방향과 일치한다. 다만 제안된 6개 섹션을 한 번에 도입하면 같은 정황이 요약·브리핑·확인 현황에 반복되고, Fact 확정/승격을 보류한 현재 정책과 충돌할 수 있다. 따라서 현재 구조를 유지한 채 표시용 projection을 먼저 보강한다.

### 이미 적용된 항목

| 제안 | 현재 상태 |
|---|---|
| 자연스러운 Current Case Snapshot | `case_context.situation_summary`와 `case_brief.summary`를 우선 사용하고, 백엔드 fallback도 한 문단으로 재구성함 |
| 주장·요구·피해 상태의 불확실성 보존 | 송금·노출 여부를 `확인 필요`, 고객 답변, 확인 결과로 구분하며 요청을 실제 수행으로 바꾸지 않음 |
| Turn 번호를 기본 화면에서 숨김 | `BriefEntry.turn`은 정렬용으로만 사용하고 기본 패널에는 발화 번호를 표시하지 않음 |
| Generic 정황의 기본 중복 축소 | 정규화·중복 제거와 source fallback을 적용함. 단, 구체 정황이 있을 때 generic 부모를 숨기는 규칙은 추가 보강 필요 |
| 미완료·완료 작업 구분 | `inProgress`를 제거하고 `미완료 / 완료` 두 lane으로 통일함 |
| 상세 업무 설명 축소 | 확장 영역에는 하위 업무 제목과 확인 방법만 표시하고 정황·담당자·시각 반복은 제거함 |
| `[...]` 행 액션의 기본 숨김 | 데스크톱에서는 평소 숨김, 행 hover·keyboard focus·메뉴 open일 때 표시. 모바일에서는 항상 표시 |
| DB/API 계약 보존 | 현재 작업은 프론트 projection·grouping 중심이며 DB schema와 공개 API를 변경하지 않음 |

### 적용 가치가 높아 다음 작업으로 남길 항목

1. **요약 아래 compact 상태 표시**
   - `송금 미확인`, `정보 노출 미확인`, `기관 확인 필요`처럼 현재 미확인 핵심만 표시한다.
   - 상세 금액과 거래 원장은 송금 기록 조회로 연결하고, 패널에서 중복 렌더링하지 않는다.
2. **피해·노출의 요청과 실제 상태 분리**
   - `인증정보 제공 요구`와 `인증정보 실제 제공 여부`를 별도 행으로 보여준다.
   - `REQUESTED/INSTRUCTED`를 `COMPLETED`로 승격하지 않는다.
3. **사실 출처 배지**
   - DB status를 새로 만들지 않고 presentation mapping으로 `[상대방 주장]`, `[고객 진술]`, `[미확인]`, `[공식 확인]`을 표시한다.
   - Fact 확정·승격 개념을 제품 판단 기준으로 부활시키는 작업은 별도 설계로 보류한다.
4. **구체 정황 우선 규칙**
   - 구체적인 기관명·요구 행동·노출 항목이 있으면 `특정 행동 요구`, `금전 이동 요구` 같은 generic 부모 항목은 기본 목록에서 숨긴다.
   - 구체 항목이 없을 때만 generic 항목을 fallback으로 표시한다.
5. **조치 결과 기록의 최소 표시**
   - 현재 서버 Task/Action에서 실제 완료된 결과가 있을 때만 `담당자 조치·결과`에 표시한다.
   - 아직 canonical event/timeline 계약이 없으면 임의의 시간·담당자 이력을 만들지 않는다.

### 현재 적용하지 않는 항목과 이유

| 제안 | 판단 |
|---|---|
| 6개 섹션으로 전면 재편 | 현재 `은행 직원 대응 가이드 + 주요 보이스피싱 정황` 구조와 중복될 가능성이 커서 보류. 먼저 피해·노출 compact view와 출처 배지를 추가한다. |
| 별도 `사칭·접촉 정보` Entity 화면 | 현재 우측 패널 계약에 사람·기관·장소 Entity projection이 충분히 연결되어 있지 않다. 없는 데이터를 추론해 만들지 않는다. |
| 별도 `사실·확인 현황`에서 CONFIRMED를 중심으로 표시 | Fact 확정·승격 체계는 제품 정책상 보류 중이다. 실제 공식 확인 결과와 고객 진술만 출처 배지로 표현한다. |
| 우측 패널의 `진행 중` 상태 lane | 제품 결정대로 `미완료 / 완료`만 유지한다. 하위 단계의 `n/m` 진행 수치로 충분하다. |
| 우측 패널에 질문·기관 확인·대응 조치 실행 UI를 확대 | 질문과 실제 업무 수행은 Chat/기존 기능 화면이 담당한다. 패널은 연결 버튼과 결과 요약만 제공한다. |
| 모든 Evidence/Turn을 기본 펼침 | 5~10초 스캔 목적과 충돌한다. 필요할 때만 상세 Evidence를 여는 후속 기능으로 둔다. |

### 필수 `[...]` 액션 표시 규칙

- 데스크톱: `right-panel-row-actions`와 `[...]` 트리거는 기본적으로 보이지 않는다.
- 해당 행에 마우스를 올리면 표시한다.
- 키보드로 행 또는 메뉴에 focus가 들어오면 표시한다.
- `[...]` 메뉴가 열린 동안은 행에서 포인터가 빠져도 계속 표시한다.
- 모바일·터치 환경에서는 hover가 없으므로 항상 표시한다.
- 메뉴는 행 제목·설명·다른 텍스트를 가리지 않도록 같은 행의 우측에 배치하고, 열린 메뉴의 z-index를 행보다 높게 유지한다.
- 이 규칙은 가이드 제목, 하위 업무, 주요 정황 항목에 공통 적용한다.

### 권장 최종 IA (최소 변경안)

```text
우측 사건 현황
├─ 현재 사건 요약 (문장형 Current Case Snapshot)
│  └─ compact 상태 표시: 송금·정보 노출·기관 확인 필요
├─ 은행 직원 대응 가이드
│  ├─ 미완료 (하위 업무 n/m)
│  ├─ 완료
│  └─ 제외·보관
└─ 주요 보이스피싱 정황
   ├─ 신분·관계
   ├─ 상황·사건 주장
   ├─ 요구 행동
   ├─ 압박·연락 통제
   ├─ 금전 관련 정황
   └─ 고객 피해·노출
```

이 구조를 유지하면서 요약 상태 배지와 출처 배지를 추가하는 것이, 현재 데모에서 가장 안전하고 빠른 개선 순서다.
