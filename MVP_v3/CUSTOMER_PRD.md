# PRD — CSR | Case Share Room Customer Frontend V3

> 보이스피싱 양방향 상담·대응 플랫폼

문서 버전: 1.0  
작성일: 2026-09-03  
상위 제품 기준: `MVP_v3/PRD.md`

---

## 0. 문서 목적

이 문서는 CSR | Case Share Room의 고객용 Frontend V3 제품 요구사항을 정의한다.

은행용 V3가 은행 담당자의 Shared Case Workspace라면, 고객용 V3는 피해자가 현재 상황을 이해하고 필요한 질문에 답하며 즉시 안전조치와 피해구제 절차를 수행하도록 돕는 **Customer Safety Workspace**다.

고객용 화면은 은행 화면의 축소판이나 내부 업무화면이 아니다. 동일한 Shared Case를 사용하되 고객에게 필요한 정보만 쉽고 안전한 언어로 제공해야 한다.

---

## 1. 제품 목표

고객이 다음 질문에 즉시 답을 얻도록 한다.

1. 지금 무엇을 멈춰야 하는가?
2. 은행 또는 AI가 무엇을 확인하고 있는가?
3. 내가 지금 답해야 할 질문은 무엇인가?
4. 이미 피해가 발생했다면 무엇부터 해야 하는가?
5. 내가 보낸 답변과 자료가 안전하게 접수됐는가?
6. 다음 단계와 현재 진행 상태는 무엇인가?

제품의 핵심 문장:

> 고객이 불안한 상황에서도 한 번에 한 가지 행동을 이해하고 실행하며, 그 결과가 같은 Shared Case를 통해 은행 대응으로 연결되는 안전 상담 화면

---

## 2. 핵심 사용자

### Primary

- 보이스피싱이 의심되는 통화·문자·메신저를 받은 고객
- 송금 또는 개인정보·인증정보 제공 여부를 아직 명확히 판단하지 못한 고객
- 이미 송금 피해가 발생해 즉시 피해구제가 필요한 고객

### 사용자 상태 특성

- 긴장하거나 판단력이 흔들린 상태일 수 있다.
- 금융·수사기관 용어를 이해하지 못할 수 있다.
- 모바일 기기를 한 손으로 사용하는 경우가 많다.
- 같은 질문을 반복해서 받으면 상담 신뢰가 크게 떨어진다.
- “예/아니요” 답변만 보이면 무엇에 답했는지 기억하기 어렵다.

따라서 짧고 직접적인 문장, 분명한 행동 버튼, 질문과 답변이 함께 남는 기록, 중복 질문 방지가 필수다.

## 3. 제품 범위

고객용 초기 V3의 핵심 화면은 하나다.

### Customer Case Room

권장 Route:

```text
/customer/cases/:caseId
```

실제 운영에서는 추측 가능한 Case ID만으로 접근할 수 없다. 만료되는 보안 상담 링크, 본인 인증 또는 인증 세션이 필요하다.

별도 Agent 선택 화면, 복잡한 고객 Dashboard, 내부 검증 화면은 만들지 않는다.

## 4. 핵심 UX 원칙

### 4.1 한 화면, 한 사건

고객은 하나의 Case 안에서 다음을 처리한다.

- 은행·상담 AI의 안내 확인
- 일반 메시지 전송
- 구조화 질문 응답
- 파일·이미지 제출
- 현재 진행 상황 확인
- 피해 발생 모드 전환
- 피해구제 절차 확인과 지원 요청
- 중요한 메시지 북마크

### 4.2 한 번에 한 가지 핵심 행동

여러 질문을 한 카드에 동시에 강요하지 않는다. 질문 Queue가 여러 개여도 고객에게는 순서대로 하나씩 보여준다.

### 4.3 중요한 문장은 한 번만 크게

다음처럼 제목과 설명으로 같은 질문을 반복하지 않는다.

```text
상대방에게 송금한 사실이 있습니까?
송금을 진행했는지 여부를 알려주세요.  ← 중복 금지
```

권장:

```text
상대방에게 송금한 사실이 있습니까?
[예] [아니요] [잘 모르겠어요]
```

필요한 보충 설명은 질문 반복이 아니라 판단 기준이나 안전 안내에만 사용한다.

### 4.4 고객 답변에는 항상 원 질문을 함께 보존

은행 담당자 화면에 `예`, `아니요`만 표시하지 않는다.

```text
질문: 인증번호·비밀번호 또는 OTP를 제공하셨나요?
고객 답변: 예
```

### 4.5 AI와 사람의 결정을 구분

- AI 추천: 확인 또는 검토가 필요한 제안
- 고객 진술: 고객이 답한 내용
- 담당자 확정: 은행 담당자가 검토한 사실
- 기관 확인: 공식 근거로 확인된 결과

고객의 답변을 즉시 공식 사실로 단정하지 않는다.

## 7. 상단 긴급 안전 영역

일반 모드에는 다음을 표시한다.

- 송금·인증정보 제공을 멈추라는 짧은 경고
- 알려진 연락처가 아니라 공식 채널로 확인하라는 안내
- `이미 사기 당했어요` 주요 버튼

버튼 명칭은 `긴급 대응 시작`이 아니라 고객이 자신의 상황을 바로 식별할 수 있는 `이미 사기 당했어요`를 사용한다.

버튼 선택 시 확인 Dialog에서 의미를 짧게 설명한 뒤 Recovery Mode로 전환한다. 중복 요청을 막기 위한 idempotency key를 사용한다.

---

## 8. Normal Mode

기본 상태는 안전 상담 모드다.

오른쪽 보조 영역에는 다음만 간결하게 표시한다.

- 현재 진행 상황
- 답변 완료 수 / 확인 대기 수
- 안전 상담 안내

`현재 확인 중 / 확인 중 / 현재 상황을 확인하고 있습니다`처럼 같은 의미의 카드를 중복 표시하지 않는다.

별도의 빈 `피해구제 안내` 카드는 기본 화면에 노출하지 않는다. 피해가 발생한 경우에만 Recovery UI를 활성화한다.

---

## 9. Recovery Mode

### 진입 조건

- 고객이 `이미 사기 당했어요` 선택
- 은행 담당자가 피해 발생을 확인
- Shared Case의 피해 상태가 서버에서 확정

### 지속성

Recovery Mode는 브라우저 localStorage가 아닌 Shared Case 서버 상태로 저장한다. 새로고침, 재접속, 다른 기기에서도 유지한다. 고객이 임의로 일반 모드로 되돌리지 않는다. 오전환 해제는 은행 담당자의 확인 흐름을 거친다.

### 전환 후 UI

- 일반 모드의 `안전 상담 안내`는 제거한다.
- 오른쪽에 `보이스피싱 피해 구제 안내` Navigator를 표시한다.
- 현재 진행 상황은 피해구제 단계로 전환한다.
- 은행 Shared Case에는 일반 채팅 메시지 대신 `고객 피해 발생 긴급 신호` Event와 Context 경고로 전달한다.

### 피해구제 Navigator

다음 네 단계만 간결하게 표시한다.

1. 즉시 연락
2. 증빙 확보
3. 신고 접수
4. 구제 신청

단계 버튼을 누르면 Navigator 아래에 내용을 계속 늘리지 않는다. Conversation의 현재 시간 위치에 해당 단계의 **상세 절차 카드**를 삽입한다.

상세 절차 카드는 다음을 포함한다.

- 단계 목적
- 지금 해야 할 순서
- 필요한 연락처 또는 공식 채널
- 준비 자료
- 주의사항
- `내 상황에 맞는 AI 조언`
- `은행 담당자에게 지원 요청`

AI 조언과 지원 요청은 외부 기관 업무를 자동 대행한 것처럼 표현하지 않는다. 실제 신고·지급정지·구제 신청에는 고객 확인, 은행 승인, 외부 기관 연동 결과가 필요하다.

---

## 10. Customer Safety Conversation

Conversation은 다음 항목을 하나의 시간순 기록으로 보여준다.

- 고객 일반 메시지
- 고객에게 공개된 은행 메시지
- 고객용 AI 안내
- 은행이 보낸 구조화 질문 카드
- 고객 답변 결과
- 고객에게 공개 가능한 검증 결과
- 피해구제 상세 절차 카드
- 첨부파일
- 고객에게 필요한 상태 Event

모든 항목은 서버 시각과 sequence를 기준으로 오름차순 정렬한다. 카드라는 이유로 채팅 상단이나 별도 고정 영역에 끼워 넣지 않는다.

은행 내부 메시지, AI 비공개 작업, 담당자 메모, 내부 위험 점수, 내부 검증 근거, 다른 고객 정보는 절대 노출하지 않는다.

## 11. 질문 카드

### 카드 구성

```text
[확인이 필요한 질문 · 2/4]

인증번호·비밀번호 또는 OTP를 제공하셨나요?

[예] [아니요] [잘 모르겠어요]
[직접 입력]

[답변 보내기]
```

필수 요소:

- 원 질문 하나
- 전체 Queue 중 현재 순서
- AI 또는 담당자가 생성한 선택지
- `잘 모르겠어요` 선택지
- 직접 입력 칸
- 단일 주요 전송 버튼
- 전송 중·성공·실패 상태

### 동작 규칙

- 한 번에 한 질문만 활성화한다.
- 답변 전송 전에는 선택을 수정할 수 있다.
- 전송 후 카드는 읽기 전용 완료 상태로 바뀐다.
- 성공 후 다음 대기 질문을 표시한다.
- 실패하면 답변 값을 보존하고 재시도 버튼을 제공한다.
- 같은 `target_field` 또는 의미상 동일 질문을 다시 만들지 않는다.
- 이미 답변됐거나 확정된 항목은 추천 후보에서 제외한다.
- 고객에게 대기 중인 은행 질문이 있으면 AI가 별도의 유사 질문을 선제 생성하지 않는다.

### AI 선제 질문

Case Orchestrator는 은행 또는 고객 화면이 열려 있지 않아도 중앙 Shared Case의 변경을 감지한다.
아직 처리하지 않은 안전 필수 항목이 있으면 아래 항목 중 P0로 판정된 질문만 자동 Queue에 등록할 수 있다.
Queue에는 여러 필수 질문이 준비될 수 있지만 고객에게는 항상 한 장만 활성화하고, 답변 후 다음 한 장을 발송한다.

- 실제 송금 여부
- 개인정보 제공 여부
- 인증정보 제공 여부
- 원격제어 앱 설치 여부

질문은 현재 Case의 기존 질문·답변·Fact를 확인한 뒤 생성한다. P0 질문은 자동 Queue 등록이 가능하지만, 중복 검사와 고객 공개 문장 검수 규칙을 통과해야 한다.
기관·연락처·계좌·사건 세부내용처럼 조사 범위가 넓거나 맥락 판단이 필요한 P1/P2 질문은 AI가 독단적으로 발송하지 않고 은행 담당자 검토를 거친다.

자동 질문의 실행 주체는 Frontend가 아니라 General API의 Case automation worker다.
따라서 고객 화면 최초 진입이나 버튼 클릭을 자동 질문 생성 조건으로 사용하지 않는다.

## 12. 고객 답변의 은행 전달

고객 답변 저장 시 다음 연결 정보를 유지한다.

```text
case_id
question_id
source_message_id
target_field
question_text_snapshot
answer_value
answer_text
answered_at
actor_user_id
actor_role
visibility
fact_candidate_id
```

은행 V3에는 얇은 구조화 카드로 표시한다.

```text
고객 답변 접수
질문: 개인정보를 제공하셨나요?
답변: 예
상태: AI 추출 후보 · 담당자 확인 필요
```

`예`처럼 답변만 단독 표시하지 않는다. 위험과 연결되는 답변이면 AI 개인 공간이라는 별도 화면에만 숨기지 않고 Shared Case Context의 `확인 필요 위험요소`에도 즉시 후보로 반영한다. 다만 담당자 확정 전에는 `확정 사실`로 표시하지 않는다.

## 13. 일반 채팅과 AI 응답

### Composer

```text
[첨부] [상대방이 요구한 내용이나 현재 상황을 입력하세요] [전송]
```

- Enter: 전송
- Shift+Enter: 줄바꿈
- 전송 중 중복 제출 차단
- 메시지 저장이 끝나면 AI 응답을 기다리지 않고 내 메시지를 즉시 대화에 표시하고 입력창을 다시 활성화
- AI는 다음 화면 프레임부터 최신 고객 공개 대화와 누적 질문·답변을 다시 읽어 백그라운드에서 응답 생성
- 연속 메시지의 AI 응답은 저장 순서대로 처리하며, AI 처리 중에도 다음 메시지를 입력할 수 있음
- 실패 시 작성 중 텍스트와 파일 보존
- 새 메시지 수신 시 사용자가 하단 근처에 있을 때만 자동 스크롤
- 과거 기록을 읽는 동안 강제로 맨 아래로 이동하지 않음

### 고객용 AI

고객 채팅은 AI 안전 안내 모드를 기본 활성화한다. 고객이 일반 메시지를 보내면 General API가 Case Orchestrator를 통해 고객 공개용 응답을 생성한다. 고객은 비용·응답 부담이 없거나 단순 자료 제출만 원하는 경우에만 토글로 안내를 끌 수 있다.

AI 응답은 다음 기준을 지킨다.

- 한 문단에 한 행동
- 쉬운 한국어
- 위협적이거나 책임을 고객에게 전가하는 표현 금지
- 확인되지 않은 내용을 사실처럼 단정하지 않음
- 송금·인증번호 제공을 요청하지 않음
- 공식 채널을 구체적으로 안내
- 내부 Agent 이름, Prompt, 위험 점수 계산 방식 비노출

AI 안전 안내가 활성화된 일반 메시지는 고객 답변을 우선 제공하되, Backend는 규칙 기반 안내·기존 Case 결과·캐시를 먼저 사용하고 실제 생성이 필요한 경우에만 제한된 호출을 수행한다.
메시지 저장 성공과 AI 응답 성공은 별도 상태로 취급한다. AI 지연이나 실패가 고객 메시지 표시와 다음 입력을 막아서는 안 된다.

## 14. 첨부파일

지원 범위:

- 이미지
- PDF
- 일반 문서
- 거래내역 캡처
- 문자·메신저 증빙

초기 제한:

- 한 메시지 최대 10개
- 파일당 최대 10MB
- 허용 MIME과 파일 signature를 서버에서 검증

저장 흐름:

```text
파일 선택
→ General API upload
→ 안전 검사
→ Attachment metadata 저장
→ attachment_id 반환
→ Message와 연결
→ AI가 권한 범위 안에서 분석 가능
```

운영에서는 Object Storage와 만료되는 서명 URL을 사용한다. 원본 파일명, MIME, 크기, checksum, uploader, Case ID, 생성 시각, 보안 검사 상태를 기록한다.

## 15. 북마크

고객은 중요한 메시지·질문·절차 카드를 북마크할 수 있다.

- 북마크 버튼은 카드마다 동일한 위치에 둔다.
- 북마크 목록은 현재 Case에서만 보인다.
- 북마크 항목을 누르면 원본 Timeline 위치로 이동한다.
- 고객 북마크는 개인 UI 상태이며 은행 업무 Fact로 취급하지 않는다.
- 여러 기기에서 유지하려면 서버 저장을 사용한다.

## 16. 현재 진행 상황

일반 모드 예시:

1. 상황 접수
2. 필요 정보 확인
3. 기관 확인
4. 보호 조치
5. 처리 완료

Recovery Mode 예시:

1. 피해 상황 접수
2. 추가 송금·접촉 중단
3. 거래내역·대화 증빙 확보
4. 은행 지급정지·신고 확인
5. 피해구제 신청

규칙:

- 완료, 진행 중, 대기를 색과 아이콘·텍스트로 함께 표현한다.
- 기술적인 Backend status를 그대로 노출하지 않는다.
- 단계 클릭 시 관련 Conversation 항목으로 이동한다.
- 단계는 고객 요청과 은행 담당자의 실제 처리 결과에 따라 갱신한다.
- 완료되지 않은 외부 신고·지급정지를 완료로 표시하지 않는다.

## 17. 공개 범위와 보안

고객 API는 `view=customer` 같은 요청 파라미터만 신뢰해서는 안 된다. 서버가 인증된 사용자와 Case 참여 권한을 검사해야 한다.

### 고객에게 공개 가능

- CUSTOMER visibility Message
- 고객 본인의 질문과 답변
- 고객 공개가 승인된 Verification 요약
- 고객용 진행 상태
- 고객용 보호·피해구제 안내
- 고객이 업로드한 Attachment

### 고객에게 공개 금지

- TEAM, BANK_INTERNAL, AI_PRIVATE Message
- 내부 Risk score 상세 계산
- 담당자 개인 메모
- AI 내부 추론·Prompt
- 미승인 Verification Evidence와 RAG 원문
- 다른 고객·직원 개인정보
- 내부 감사·시스템 로그

민감정보는 화면 로그와 브라우저 Console에도 출력하지 않는다.

## 19. General API와 AI API 역할

```text
Customer Frontend
  ↓
General API
  ├─ 인증·권한·공개 범위
  ├─ Case·Message·Question·Fact·Attachment 저장
  ├─ 상태 전이·중복 방지·감사 Event
  └─ 필요한 경우 AI API 오케스트레이션
        ├─ 질문 생성
        ├─ 고객 답변 구조화
        ├─ 쉬운 설명 생성
        └─ 피해구제 맞춤 안내
```

Customer Frontend가 AI API를 직접 호출하지 않는다.

초기에는 기존 General API 계약을 우선 재사용한다. 필요한 계약이 없으면 연결된 것처럼 Mock 처리하지 않고 API gap을 문서화한 뒤 Backend와 함께 추가한다.

## 21. 오류·로딩·빈 상태

### 초기 로딩

```text
안전 상담 정보를 불러오고 있습니다.
```

### AI 처리 중

```text
현재 상황에 맞는 안내를 준비하고 있습니다.
```

### 질문 없음

```text
현재 답변을 기다리는 질문이 없습니다.
추가 확인이 필요하면 이 화면에 안내해 드립니다.
```

### 부분 오류

채팅 조회가 성공하고 AI 안내만 실패했다면 채팅 전체를 막지 않는다. 해당 영역에만 재시도를 제공한다.

### 요청 실패

`요청을 처리하지 못했습니다`만 표시하지 않는다.

권장:

```text
답변을 저장하지 못했습니다.
입력한 내용은 유지했습니다. 잠시 후 다시 시도해 주세요.
[다시 시도]
```

### 연결 끊김

- 화면 상단에 연결 상태 표시
- 작성 내용 보존
- 자동 재연결
- 서버 확인 전 성공으로 표시하지 않음

## 22. 접근성과 사용성

- 본문 최소 16px 권장
- 주요 터치 영역 최소 44×44px
- 위험·완료 상태를 색만으로 전달하지 않음
- 질문 Card에 `fieldset`, `legend`, 명확한 label 사용
- 키보드만으로 선택·직접 입력·전송 가능
- Screen Reader에 질문 순서와 전송 결과 알림
- Dialog focus trap, Escape 닫기, 닫힌 뒤 호출 버튼으로 focus 복귀
- `prefers-reduced-motion` 존중
- 긴 URL·파일명·기관명 overflow 방지
- 고령 사용자에게 작은 회색 보조문구 남발 금지

---

## 23. 반응성과 성능

- Route 전환 즉시 Skeleton 또는 기존 Case shell 표시
- 메시지 전송 시 낙관적 UI를 사용하더라도 서버 실패 시 명확히 복구
- AI 호출은 사용자 행동과 필요한 Case Event가 있을 때만 수행
- Case polling이 필요하면 AI 생성 endpoint를 polling 대상에서 제외
- 은행·고객 입력은 먼저 General API를 통해 중앙 DB에 저장하고 Case `updated_at`을 갱신
- Case automation worker는 DB 변경 지문이 달라진 Case만 재평가
- 고객 화면은 4초, 은행 Case 화면은 5초 이내에 같은 Shared Case Bundle을 다시 조회
- 새 데이터 전체를 매번 다시 그리지 않도록 entry ID 기반 병합
- 긴 Conversation은 virtualization 또는 구간 로딩 적용
- 첨부 미리보기는 지연 로딩

## 24. 주요 사용자 시나리오

### Scenario A — 피해 여부 확인 전

```text
고객 보안 링크 접속
→ 안전 안내 확인
→ 은행 질문 Card 수신
→ 질문과 선택지를 함께 확인
→ 답변 전송
→ 다음 질문 표시
→ 진행 상황 갱신
→ 은행 Shared Case에 원 질문+답변 후보 반영
```

### Scenario B — 고객 일반 메시지

```text
고객이 상대방 요구 내용 입력
→ Message 저장
→ Case Orchestrator가 기존 Context와 중복 여부 확인
→ 필요한 경우 쉬운 안전 안내 또는 다음 질문 생성
→ 고객 Conversation과 은행 Shared Case 갱신
```

### Scenario C — 이미 피해 발생

```text
이미 사기 당했어요
→ Recovery Mode 서버 저장
→ 일반 안전 안내 제거
→ 피해구제 Navigator 표시
→ 은행 Case에 긴급 Event·Context 경고 반영
→ 고객이 즉시 연락 선택
→ 상세 절차 Card를 Conversation에 시간순 삽입
→ 은행 지원 요청
→ 실제 처리 결과에 따라 진행 단계 갱신
```

### Scenario D — 증빙 제출

```text
고객이 이미지·PDF 선택
→ 개수·용량 즉시 검증
→ 서버 안전 upload
→ Message와 연결
→ 고객에게 접수 상태 표시
→ 은행 담당자가 같은 Shared Case에서 확인
```

### Scenario E — 정상·낮은 위험

정상 상담에서는 Recovery와 고위험 적색 UI를 강요하지 않는다. AI는 추가 위험 근거가 없음을 쉬운 문장으로 설명하고 공식 채널 확인 정도만 안내한다.

## 26. Definition of Done

고객용 V3는 다음 조건을 모두 충족해야 완료로 판단한다.

- [ ] V3 고객 Route가 은행 V3와 독립적으로 정상 실행됨
- [ ] Case ID만으로 접근할 수 없고 인증·Case 참여 권한을 검사함
- [ ] Customer Bundle에 내부 Message·Fact·Evidence가 포함되지 않음
- [ ] Conversation이 넓은 주 영역으로 유지됨
- [ ] 모든 Message와 Card가 하나의 시간순 규칙을 따름
- [ ] 과거 기록 열람 중 강제 하단 이동이 없음
- [ ] Enter 전송, Shift+Enter 줄바꿈이 동작함
- [ ] 은행 질문이 고객 질문 Card로 전달됨
- [ ] 질문 문장이 중복 표시되지 않음
- [ ] 선택지·잘 모르겠어요·직접 입력을 지원함
- [ ] 답변이 원 질문과 함께 은행 V3에 표시됨
- [ ] 이미 확인한 항목을 다시 질문하지 않음
- [ ] AI 선제 질문이 기존 Queue와 충돌하지 않음
- [ ] `이미 사기 당했어요`가 Recovery Mode를 서버에 저장함
- [ ] Recovery Mode가 새로고침·재접속 후에도 유지됨
- [ ] 일반 안전 안내가 Recovery 안내로 정확히 교체됨
- [ ] 피해구제 Navigator는 채팅창 밖 보조 영역에 있음
- [ ] 선택한 피해구제 상세 절차는 Conversation에 시간순 Card로 생성됨
- [ ] 고객 긴급 신호가 은행 Case Event와 Context에 반영됨
- [ ] 진행 단계 클릭 시 관련 Conversation 항목으로 이동함
- [ ] 첨부 업로드·표시·실패 복구가 동작함
- [ ] 북마크와 원본 항목 이동이 동작함
- [ ] AI 실패가 전체 채팅을 막지 않음
- [ ] General API를 통해서만 AI를 호출함
- [ ] 유료 API 호출·토큰·재시도·동시성 상한이 적용됨
- [ ] 정상·낮은 위험 Case에 과도한 경고가 없음
- [ ] 모바일에서 Composer와 고정 버튼이 겹치지 않음
- [ ] Type Check·Build·계약 테스트·E2E가 통과함
- [ ] Console Error와 주요 Mock·TODO·충돌 마커가 없음

---

## 27. Non Goals

초기 고객용 V3 범위가 아니다.

- 음성 통화 상담 기능
- 통화 녹음·실시간 STT UI
- 고객이 내부 Agent를 선택하는 기능
- 은행 내부 채팅·메모 노출
- 내부 Verification Evidence 원문 노출
- 고객용 복잡한 사건 관리 Dashboard
- AI가 승인 없이 지급정지·신고·이체를 실제 실행하는 기능
- 경찰·금융기관의 기존 피해구제 시스템 대체

음성 통화 기능은 향후 확장 항목으로만 기록하고 현재 UI에서는 숨긴다.

---

## 28. 최종 제품 원칙

고객용 V3의 성공은 기능 개수나 화려한 AI 표현으로 판단하지 않는다.

고객이 불안한 상황에서도:

- 무엇을 멈춰야 하는지 알고,
- 무엇에 답하는지 이해하며,
- 답변과 자료가 안전하게 접수됐음을 확인하고,
- 이미 피해가 발생했다면 다음 절차를 놓치지 않고,
- 은행 담당자의 대응과 하나의 Shared Case로 연결되는 것

이 최종 목표다.
