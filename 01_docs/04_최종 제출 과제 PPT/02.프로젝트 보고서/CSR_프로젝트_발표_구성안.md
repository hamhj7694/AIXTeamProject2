# CSR 프로젝트 발표 구성안

CSR · Case Share Room / 보이스피싱 양방향 상담·대응 플랫폼  
작성일: 2026-09-11  
용도: 팀원이 실제 내용과 근거를 채워 넣는 발표용 마스터 개요

## 1. 발표의 중심 주장과 사용법

**CSR은 범죄자의 발화 맥락과 고객 답변·검증 결과를 Shared Case에 모아, 은행 담당자의 사건 파악·확인·고객 설득·대응 기록을 지원하는 AI 솔루션이다.**

발표는 다음 질문에 답하도록 구성한다.

1. 어떤 고객·은행 업무 문제를 해결하려 했는가?
2. 그 문제를 어떤 데이터와 기술로 다루었는가?
3. ML·LLM·검색·일반 코드가 각각 무엇을 맡았는가?
4. 공모전 제출 시점에 무엇을 공개했고, 실제로 무엇이 작동했는가?
5. 어떤 한계를 발견해 무엇을 바꾸었고, 어떤 근거로 개선을 확인했는가?

이 문서의 ‘필수’는 참고 발표자료와 CSR 개발 발표 목적에 따른 권장 기준이다. 공식 심사표의 의무 항목을 확인한 결과는 아니다.

본문 32장은 내용을 빠뜨리지 않기 위한 마스터 구성이다. 32장을 모두 같은 비중으로 발표할 필요는 없다. 실제 발표 시간에 맞춰 합치고, 상세 실험·API·피처 목록은 부록으로 이동한다.

대괄호 `[ ]`는 팀에서 확인해 채울 정보다. 수치·완료 여부·채택 이유를 임의로 채우지 않는다. 2026-09-08 기준 CSR 기술·서비스 명세는 설계와 구현을 설명하는 근거로 사용했으며, 현재 실행 서버를 직접 검사한 결과는 아니다.

## 2. 참고자료에서 가져올 구성 방식

페이지는 PDF의 물리적 페이지 번호다. 참고자료의 구성 방식을 활용하되, 해당 팀의 분석 방법이나 성과 수치가 CSR에도 타당하다고 가정하지 않는다.

| 참고 발표자료 | 확인한 구성 | CSR에 적용할 부분 |
|---|---|---|
| FlowCast · PM 수요예측, 71p | 일정·워크플로우·역할 7~9p, 모델 비교·선정 25~26·39·53·57p, 웹 시연 59~65p, 한계·계획 69p | 팀이 어떤 과정을 거쳐 모델을 서비스로 연결했는지 한눈에 보여준다. |
| 직파머스 · 농수산물가격예측, 55p | 역할·일정·환경 7~9p, 수집·매핑·전처리 13~19p, 피처 확정 30p, 튜닝·모델 비교 32~40p, 서비스 흐름 43~44p, 한계 54~55p | 데이터 처리 이유와 기술 선택 이유를 제시하고, 서비스 호출 흐름까지 연결한다. |
| MBCA 1차 팀 프로젝트 1조 · 부산 관광·폐업 분석, 64p | 가설·데이터 기준 10~16p, 가설 판정 18~22p, 누수 방지·검증·선정 42~51p, 결과 해석 54~63p | 가설이 틀리거나 더 복잡한 모델이 불리한 결과도 보여준다. v2 채택 논리의 참고가 된다. |
| 2조 B2B · 수요예측·재고관리, 61p | 전체 흐름 8p, 모델 개발·선정 25~34p, 예측을 재고·발주 정책에 연결 36~49p, 서비스·한계 51~60p | ML 점수가 실제 질문·확인 우선순위·업무 지원으로 어떻게 연결되는지 설명한다. |
| 4조 · 아동학대 사전예측 솔루션, 25p | 두 분석 경로의 통합 6p, 전처리·평가·점수구간 8~14p, 변수 축소·누수 제외 17~20p, 결과 화면 24p | Window/Cumulative의 구분, 변수 선택, 임계값과 표시 등급의 연결을 설명한다. 타깃 정의에 따른 성능 해석 범위도 함께 밝힌다. |

공통 뼈대는 `문제·목표 / 데이터 / 모델 / 서비스 / 결과·한계`다. CSR에는 **LLM 추출 품질, 학습과 실행의 연결, Shared Case 오케스트레이션, 제출 전후 개선**을 추가한다.

## 3. 개발 단계와 발표 파트를 구분한다

개발 이력은 아래 단계로 정리하되, 발표는 먼저 문제·목표·서비스를 소개한 뒤 데이터와 기술로 들어간다. 청중이 CSR의 용도를 이해하기 전에 수집 코드부터 설명하지 않는다.

| 개발 단계 | 이 단계에서 설명할 일 | 완료를 보여줄 근거 |
|---|---|---|
| 0. 데이터·AI 기반 구축 | 데이터 수집/RPA, 정제, EDA, 이벤트·피처 설계, ML 실험, LLM 추출 개선 | 데이터 목록, 실행 로그, 전후 건수, 피처 계약, 실험 결과 |
| 1. 공모전 1차 제출 | 당시 공개한 소개 영역과 제출 산출물, 당시 실제로 작동한 기능 | 제출일, 제출 파일·영상, 배포 버전, 해당 시점 화면 |
| 2. 한계 진단·우선순위 | 실제 사용·테스트에서 발견한 오탐, 추출 오류, 동기화·업무 흐름 문제 | 실패 사례, 이슈, 재현 조건, 우선순위와 완료 기준 |
| 3. 개선·기능 고도화 | 데이터/ML/LLM, Shared Case, 화면·백엔드 개선 | 변경 전후 코드·화면·결과, 동일 조건 재검증 |
| 4. 최종 검증·다음 단계 | 통합 시연, 측정 결과, 남은 한계와 외부 연동 계획 | 최종 시연, 테스트 기록, 미완료 목록 |

‘로그인 전 심사위원 소개까지’는 **당시 발표·공개 범위**로 적는다. 소개 페이지까지만 보여주었다는 것과, 전체 서비스가 그 범위까지만 구현되었다는 것은 별개의 사실이다.

| D. ML·LLM 개발과 검증 | 14~19 | 입력을 어떻게 만들고, 모델과 임계값을 왜 선택했는가? |

| G. 제출 이후 개선과 고도화 | 25~28 | 왜 바꾸었고, 무엇이 얼마나 달라졌는가? |
| H. 최종 시연·검증·한계·성과 | 29~32 | 지금 무엇이 작동하며, 어디까지 입증했는가? |

### A. 프로젝트 소개와 문제·목표 · 1~6p

| 페이지·제목 | 한 장 안에 반드시 넣을 내용 | 준비할 근거·권장 형식 |
|---|---|---|
| 1. CSR 프로젝트 소개 | 서비스명, 팀명, 한 문장 정의, 발표일 | 로고와 대표 화면 1개. 기능 목록은 다음 장으로 넘긴다. |
| 2. 팀원과 책임 | 이름, 주 역할, 맡은 기능, 본인 산출물, 협업 경계 | `담당자 / 책임 / 실제 산출물` 표. PM·기획·데이터·ML·AI·프론트·백엔드가 누구에게 연결되는지 표시한다. |
| 3. 프로젝트 기간과 진행 단계 | 전체 기간, 공모전 제출일, 개선 기간, 현재 기준일, 단계별 목표·완료 상태 | 마일스톤 타임라인. 계획과 실제 완료를 구분한다. |
| 4. 해결할 문제 | 고객은 조작된 정보·압박 속에서 오판할 수 있음. 은행은 사건 맥락 재구성·확인·고객 설득·전달 부담이 있음 | 고객·은행 관점 2개 영역. 핵심 통계/팀 분석 1~2개와 출처. |
| 5. 기존 업무와 CSR 적용 구간 | 탐지 이후 누가 무엇을 재확인·전달하는지, CSR이 도울 구간 | 기존 업무 흐름과 병목 표시. 일반화한 흐름은 기관별 실제 프로세스와 구분한다. |
| 6. 프로젝트 목표와 성공 기준 | 기능 목표, 기술 검증 목표, 업무 개선 가설, 이번 프로젝트 범위 | 사건 파악 시간·확인 누락·반복 질문·추출 품질 등 `목표 / 측정 방법 / 현재 측정 여부`. |

4~6p의 논리는 ‘고객의 판단이 왜곡될 수 있고, 은행의 확인·설득에도 맥락과 시간이 필요하다. CSR은 발화 맥락을 먼저 구조화해 그 업무를 돕는다’로 연결한다. 실제 피해 감소나 설득 성공률 향상은 측정 없이 성과로 단정하지 않는다.

### B. 전체 서비스와 기술 설계 · 7~9p

| 페이지·제목 | 한 장 안에 반드시 넣을 내용 | 준비할 근거·권장 형식 |
|---|---|---|
| 7. CSR 사용 흐름과 핵심 화면 | 입력, 사건 브리프, 고객 확인, 검증 기록, 직원 판단, 종결/Recovery | 고객·은행 화면 미리보기. 은행 화면은 `사건 브리프 / 확인계획 / 고객확인 결과 / 최종조치 기록` 중심. |
| 8. 전체 시스템 구조 | Frontend, Nginx, General Backend, AI Backend, ML·LLM·검색, MySQL, 배포 구성 | 전체 구조도 1개. AI 결과 반환과 DB 저장의 책임을 분리한다. 현재 연결과 향후 외부 연결을 구분한다. |
| 9. 기술 선택과 역할 | 사용 기술, 적용 위치, 입력·출력, 필요 이유, 대안 대비 선택 이유 | 도구 로고 나열 대신 `기술 / 적용 위치 / 하는 일 / 선택 이유` 표. 세부 버전은 부록. |

### C. 데이터 수집·RPA·전처리·EDA · 10~13p

| 페이지·제목 | 한 장 안에 반드시 넣을 내용 | 준비할 근거·권장 형식 |
|---|---|---|
| 10. 데이터 구성과 사용 목적 | 문제정의용 통계·연구, 통화 분석/학습 데이터, 정상 대화, 테스트 시나리오, 사건 내부 검색 자료 | `데이터 / 출처 / 기간·건수 / 원본 단위 / 사용 목적` 표. 실제로 사용한 자료만 표시한다. |
| 11. 수집과 자동화 | 수동/API/RPA 중 실제 수집 방식, 반복 작업, 자동화 범위, 실패·중복 처리, 원본 보존 | 자동화 전후 작업 흐름, 실제 도구명·수집 로그·전후 건수. RPA 사용 이력이 없으면 미사용으로 적는다. |
| 12. 정제·라벨링·데이터 제한 | 중복·결측·포맷 처리, 발화 구분, 정상/사기 라벨 기준, 출처 편향, 제외 데이터와 이유 | `원본 건수 / 제외 이유·건수 / 최종 건수` 표와 통화 1건의 변환 예시. |
| 13. EDA가 바꾼 설계 | 사칭·주장·요구·압박 신호, 등장 순서, 정상/사기 차이, 관측 누락 등 실제 확인한 결과 | 핵심 그래프 2~3개. 각각 `관측 / 해석 범위 / 피처·질문·서비스에 반영한 결정`을 붙인다. |

전처리는 모든 작업을 나열하기보다 결과에 영향을 준 선택을 설명한다. 플래그 변수에 스케일링을 적용했는지 등은 모델·데이터 특성과 실제 코드에 따라 적는다. ‘데이터가 많다’는 설명 대신 원본 통화 수와 파생 Window 수를 별도로 제시한다.

### D. ML·LLM 개발과 검증 · 14~19p

| 페이지·제목 | 한 장 안에 반드시 넣을 내용 | 준비할 근거·권장 형식 |
|---|---|---|
| 14. 원문에서 최종 ML 피처까지 | 발화/이벤트 구조화, 후보 컬럼 정리, 파생변수 생성, 최종 입력. 각 단계의 사람·규칙 코드·LLM·ML 역할 | 통화 일부, 추출 JSON 일부, 최종 벡터의 대응 예시. `원본 컬럼 / 후보 / 최종`과 제외 이유·선택 주체. |
| 15. LLM 추출 개선 과정 | 초기 오류, 추출 기준·프롬프트·예시·Schema 변경, 부정·인용·거절·미확인 처리, 수정 전후 품질 | 동일 대화의 정답·개선 전·개선 후 비교. 모델 가중치 학습을 하지 않았다면 ‘파인튜닝’ 대신 ‘프롬프트·추출 규칙 개선’. |
| 16. ML 문제 정의와 학습 설계 | Window/Cumulative의 입력 범위와 타깃 의미, 비교 모델, 학습·검증·시험 분리, 누수 방지 | 학습 파이프라인과 분할도. 동일 통화의 구간이 학습·시험에 동시에 들어가지 않도록 한 근거. |
| 17. v1·v2·v3 실험과 v2 채택 | 버전별 변경점, 공통 평가 조건, 성능, 오탐·미탐·안정성, v3 미채택 사유 | 비교표 1개와 결정적 오류 사례 1개. v2 채택은 사용자 결정으로 반영하되 이유·수치는 실제 로그로 채운다. |
| 18. 임계값과 최종 모델 연결 | 임계값 후보, 검증 자료에서의 선택 기준, 등급별 동작, 독립 시험 결과, 학습 모델과 웹 실행 모델의 일치 | 임계값별 Precision·Recall·오탐 비교, 단계별 시나리오 점수 곡선, 모델 파일·피처 버전·실행 설정 대응. |
| 19. 업무용 LLM과 검색 구조 | 사건 요약, 질문·업무 초안, 고객 설명, 보고서의 입력·출력. 검색 대상·방법·사용자 공개 범위 | 기능별 I/O 표와 근거 포함 출력 예시. 문서 기준 현재 검색은 동일 Case 내부 TF-IDF 방식. |

ML 실험과 서비스 구현을 연결하는 핵심은 **최종 학습 피처의 이름·순서·자료형·집계 규칙과 실행 입력이 같다는 것**이다. LLM이 매번 임의의 숫자 점수를 생성해 ML에 전달하는 구조로 설명하지 않는다. 현재 코드가 실제로 수행하는 변환을 표시한다.

임계값을 낮추면 미탐뿐 아니라 오탐·확인 업무량이 어떻게 변하는지 함께 본다. 학습/검증 자료에서 기준을 선택하고, 별도로 남긴 시험 자료에서는 선택한 기준의 결과를 보고한다. 시험 결과를 보고 다시 조정했다면 그 자료는 더 이상 최종 독립 시험셋이 아니다.

Window와 Cumulative의 점수 분포가 다르면 각각 검증한다. 최고 Window 점수를 사용하는 경우에는 Window 단위 성능뿐 아니라 통화 1건 전체에서 경고가 한 번이라도 뜨는 비율도 확인한다. 표시 점수는 보정·검증 없이 현실의 범죄 확률과 동일하다고 설명하지 않는다.

## 6. 검증을 구분해 설명하는 기준

| 검증 층위 | 질문 | 권장 근거 | 해석 범위 |
|---|---|---|---|
| 데이터·라벨 | 무엇을 정답으로 학습했나? | 라벨 생성 기준, 정상·사기 구성, 검수 내역, 중복 통화 확인 | 원본 통화와 파생 구간 수를 구분. 인위적 규칙 라벨은 그 규칙 재현 성능일 수 있음. |
| ML | 위험 신호를 얼마나 잘 구분하나? | Recall·Precision·F1·PR-AUC, 혼동행렬, 통화별 오탐·미탐 | 표본·분포·분할 방식에 한정. Accuracy 한 숫자로 마무리하지 않음. |
| LLM | 사건 정보를 정확히 추출·설명하나? | 항목별 정답 비교, 누락·환각·근거 인용·Schema 통과 | 형식 유효성과 내용 정확성을 구분. |
| 통합 서비스 | 입력부터 사건·고객 답변·은행 업무까지 이어지나? | E2E 시나리오, 실제 모델 로딩, 상태·공개 범위·장애 동작 | 기능 작동 확인과 실제 현장 효과는 별개. |
| 업무 효과 | 사건 파악·확인 준비·기록 부담이 줄었나? | 동일 사례/과업에서 기존 방식 대비 시간·누락·반복 질문 비교 | 참가자 수·역할·과제 난이도·순서 효과를 적음. 미실시하면 검증 계획으로 제시. |

ML 발표에 꼭 반영할 점:

- 같은 원본 통화와 그 변형·Window가 학습과 시험에 섞이지 않도록 그룹을 관리한다.
- 앞부분 위험을 평가할 때는 그 시점까지의 정보만 사용한다. 전체 통화를 보고 만든 요약이 앞부분 피처에 유입되지 않게 한다.
- ‘통화 전체가 사기였는가’와 ‘현재 구간에 식별 가능한 위험 신호가 있는가’는 서로 다른 정답 정의다. Window 라벨을 어떻게 부여했는지 설명한다.
- 정상·경계·사기 시나리오는 동작과 실패 양상을 보는 데 유용하다. 팀이 만든 시나리오 몇 건만으로 실제 통화 탐지 성능을 일반화하지 않는다.
- 정상 비교 자료가 부족하면 실제 오탐률 추정의 제한을 밝힌다.
- 최종 학습 모델, LLM 추출기, 임계값, 웹 실행 모델을 같은 평가 단위로 연결한다.

기존 통신 AI·ASAP·FDS가 통화 맥락을 ‘전혀 보지 못한다’고 단정하지 않는다. CSR의 주장은 은행 확인 업무에 필요한 발화 맥락·고객 답변·검증 결과를 사건 단위로 활용하도록 돕는 데 집중한다. 기존 체계의 구체적 공개 기능을 발표에서 인용할 때는 해당 공식 자료와 기준일을 붙인다.

## 8. 슬라이드 형식과 부록

### 본문 공통 형식

1. 상단: 이 장의 주제를 명확히 적는다. 분석 결과가 있는 장은 근거가 뒷받침하는 결론을 제목으로 사용할 수 있다.
2. 중앙: 구조도·전후 비교·성능표·화면 등 핵심 증거 한 덩어리를 둔다.
3. 하단: 이 결과로 내린 결정 또는 다음 파트와의 연결을 한 문장으로 적는다.
4. 출처 영역: 데이터/문서 기준일, 평가셋, 버전, 실제 구현·실험·향후 계획 중 해당 상태를 표시한다.

페이지 종류별 양식:

| 종류 | 읽히는 순서 |
|---|---|
| 데이터·EDA | 질문 → 관측 결과 → 해석 범위 → 설계 반영 |
| 모델·기술 선택 | 목적 → 비교 조건 → 결과 → 선택 이유 |
| 기능 구현 | 사용자 행동 → 입력 → 처리 주체 → 출력 → 화면/저장 변화 |
| 고도화 | 관측 문제 → 원인 → 변경 → 같은 조건의 검증 → 남은 한계 |
| 성과 | 당초 목표 → 구현 산출물 → 측정 결과 → 미검증 효과 |

큰 코드 캡처·전체 JSON·환경 패키지 목록을 본문 설명의 중심으로 두지 않는다. 피처·그래프·수치·프로세스는 가능한 한 편집 가능한 표·차트·도형으로 만든다. 화면 캡처는 실제 동작을 보여줄 때 필요한 부분을 강조해서 사용한다.
