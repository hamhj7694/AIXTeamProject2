# CSR 보이스피싱 여부·위험도 분석 ML 구현 과정 및 역할

> 용도: 프로젝트 결과 보고서와 공모전 서류 심사 발표자료의 ML 설명 슬라이드 초안
>
> 기준: 2026-09-30 현재 저장소 코드·모델 계약·프로젝트 발표 구성안·확인 가능한 Notion 기록

## 1. 발표용 결론

우리 ML 경로는 통화 원문을 곧바로 `사기 확률`로 바꾸는 단일 모델이 아니다.

```text
통화/전사
  → 문장별 위험 이벤트 구조화
  → Window 단위 수치 피처 집계
  → Window Logistic 추론
  → 무신호·금전 단독 가드레일
  → 위험 점수·NORMAL/PHISHING·근거·모델 메타데이터
```

현재 웹 실행부가 로드하는 모델은 `WINDOW_LOGISTIC_DASHBOARD_EXPERIMENTAL_SAMPLE_v1.pkl`이다. 모델 계약상 `model_name=Logistic`, `unit=Window`, `feature_version=v2.2`, `model_version=12_07_recall_first_v1.0`, `model_status=EXPERIMENTAL_SAMPLE`로 기록되어 있다. 따라서 발표에서는 “실험용 Window Logistic artifact를 서비스 실행부에 연결해 검증했다”고 표현하고, 이 저장소만으로 새 학습을 재현했다고 표현하지 않는다.

노션에서 확인되는 데이터 기록은 **발췌 통화 776건을 확보하고 자동 추출과 LLM 분류로 SILVER 데이터를 만든 과정**이다. 다만 해당 기록과 현재 저장소에서 특정 RPA 도구, 실행 로그, 수집 전후 건수는 확인되지 않았다. 따라서 “RPA로 776건을 수집했다”고 단정하지 않고, 실제 RPA 로그가 확보된 경우에만 도구명과 수치를 추가한다.

## 2. 한 장짜리 PPT 원고

### 슬라이드 제목

**원문을 위험 신호와 수치로 바꾸는 보이스피싱 ML 판단 구조**

### 부제

**통화·전사 → 이벤트·피처 → 10-turn Window Logistic → 가드레일 → 위험 점수와 대응 근거**

### 왼쪽: 구현 흐름

1. **입력**
   - 발췌 통화와 전사 텍스트를 분석 단위로 사용한다.
   - 현재 PoC는 구조화된 이벤트와 데모 입력을 지원한다.
   - 운영 연동 시 원문을 외부 서비스로 그대로 보내지 않고, 온디바이스 또는 통신 영역에서 추출한 개인정보 보호형 분석 스키마를 받는 구조를 전제로 한다.

2. **위험 이벤트 추출**
   - 사칭: 검찰·경찰·은행 등 권위기관 또는 금융기관 사칭
   - 심리 전략: 권위, 공포, 긴급성, 정당성, 개인정보 추출
   - 행동 요구: 민감정보·인증정보 요구, 연락 제한, 고위험 행동
   - 금전: 이체·인출·현금 전달과 금액 언급

3. **피처 빌딩**
   - 이벤트의 존재 여부, 반복 횟수, 다양성, 금액 집계, 신호 간 상호작용을 수치화한다.
   - Window 기본 길이는 `WINDOW_TURNS=10`이다. 각 시점에서 최근 10개 발화를 누적해 현재까지 관측된 위험을 계산한다.

4. **ML 추론과 안전장치**
   - 고정된 피처 이름·순서로 `predict_proba`를 실행한다.
   - artifact 임계값은 `0.95`이며, 타깃 매핑은 `0=NORMAL`, `1=PHISHING`이다.
   - 후보 신호가 하나도 없으면 점수를 제한하고, 금전 신호만으로 사기 판정을 내리지 않도록 가드레일을 적용한다.

5. **출력**
   - 원점수·최종 점수·임계값·판정 라벨
   - 사용된 이벤트와 근거, 모델 버전, 가드레일 플래그, 경고
   - 최종 금융 조치는 ML이 자동 확정하지 않고 직원 확인과 업무 절차로 이어진다.

### 오른쪽: 기술·역할 요약

| 구간 | 실제 구현·역할 | 발표 문장 |
|---|---|---|
| 데이터 | 발췌 통화·전사·CSV 확보, 자동 추출·LLM 분류 SILVER | “원본 확보와 라벨 품질을 분리해 관리했다.” |
| 이벤트 | `ExtractedEvent`와 사칭·심리·행동·금전·금액 family | “문장을 설명 가능한 사건 신호로 바꿨다.” |
| 피처 | `features_from_events()`가 반복·다양성·금액·상호작용을 계산 | “학습 피처와 실행 피처의 계약을 고정했다.” |
| ML | scikit-learn Pipeline 기반 Window Logistic | “실험용 모델을 서비스 adapter에서 검증·실행했다.” |
| 안전장치 | 무신호 점수 제한, 금전 단독 신호 제한, 임계값·해시 검증 | “높은 점수 하나만으로 자동 조치하지 않게 했다.” |
| 서비스 | AI API가 위험 점수와 근거를 반환하고 사건·업무 화면에 표시 | “분석 결과를 사람이 검토할 수 있는 사건 정보로 연결했다.” |

## 3. 학습 데이터와 자동화 과정을 설명하는 팩트 기준

| 단계 | 확인된 사실 | PPT에 쓸 표현 | 확인이 더 필요한 항목 |
|---|---|---|---|
| 원천 확보 | Notion 기록에 발췌 통화 776건이 기재되어 있음 | “발췌 통화 776건을 확보해 분석 기반을 마련했다.” | 원본 음성·전사 파일 목록, 수집 기간, 정상 대화 수 |
| 수집 방식 | 현재 확인 자료에는 수동/API/RPA를 확정할 실행 로그가 없음 | “원천 음성·전사·CSV를 확보한 뒤 자동 처리 파이프라인을 적용했다.” | RPA 도구명, 작업 URL, 실행 시각, 성공·실패·중복 건수 |
| 자동 처리 | 자동 추출과 LLM 분류로 SILVER 데이터 생성 기록이 있음 | “자동 추출·LLM 분류로 이벤트 후보와 SILVER 라벨을 만들었다.” | 라벨 검수 표본, 사람 수정 건수, 라벨 기준 버전 |
| 이벤트 구조화 | 코드에 `IMPERSONATION`, `PSY_STRATEGY`, `ACTION_REQUEST`, `MONEY_MOVEMENT`, `AMOUNT`가 있음 | “발화에서 사칭·심리·행동·금전 이벤트를 추출했다.” | 실제 전체 이벤트별 분포와 누락률 |
| 피처 생성 | 코드가 반복·다양성·금액·상호작용 피처를 계산 | “이벤트를 Window 피처 벡터로 집계했다.” | 학습 시점의 원본 피처 목록과 현재 계약의 차이 |
| 모델 연결 | 실행 artifact와 SHA-256, sklearn 1.6.1, 임계값이 저장소에 있음 | “모델 계약과 해시를 검증한 뒤 AI API에서 실행했다.” | 학습 노트북·실험 로그·학습/검증/시험 분할 |

### RPA 관련 안전한 서술

현재 근거만으로는 아래처럼 쓴다.

> “공개·확보된 통화/전사 자료를 기준으로 자동 추출 및 LLM 분류를 수행해 SILVER 분석 데이터를 만들었다. RPA를 이용한 원천 수집은 실행 도구와 로그를 확인한 뒤 별도 기재한다.”

팀에 실제 RPA 증빙이 있다면 다음 4개를 채운 뒤 문장을 바꾼다.

```text
도구명: [예: Selenium / Playwright / UiPath / n8n 등 실제 사용 도구]
수집 대상: [사이트·페이지·파일 목록]
실행 증빙: [스크립트·워크플로우·실행 로그·실행일]
전후 수량: [수집 시도 N / 성공 N / 중복·제외 N / 최종 N]
```

`n8n`은 확인된 Notion 기록에서 신뢰할 사람 알림·응답 리마인더 workflow 계획으로 설명되어 있으며, ML 학습 데이터 수집 도구로 확인되지 않는다. `Airbyte`도 현재 프로젝트의 데이터 수집에 사용하지 않은 것으로 기록되어 있다.

### 학습과 실행을 혼동하지 않기

- 현재 저장소에는 모델 **실행·검증 코드**와 모델 artifact가 확인된다.
- 저장소만으로 학습 당시의 전체 원본, 학습/검증/시험 분할, v1·v2·v3별 수치, RPA 수집 로그를 재현할 수는 없다.
- 따라서 “모델을 새로 학습했다”보다 “학습 artifact를 피처 계약과 함께 서비스에 연결하고 실행 검증했다”가 현재 코드에 맞다.
- 팀이 별도 학습 노트북·실험 로그를 보유하고 있다면, 그 자료를 확인한 뒤 학습 담당자의 실제 기여와 v2 채택 근거를 추가한다.

> “데이터 담당은 출처와 원본 단위를 관리하고, 정제·EDA 담당은 발화와 라벨의 기준을 만들었습니다. 이벤트 담당은 비정형 문장을 사칭·심리·행동·금전 신호로 구조화했고, ML 담당은 이를 Window 피처로 집계해 Logistic artifact와 임계값을 검토했습니다. AI 백엔드는 같은 피처 계약을 실행부에서 검증하고 가드레일을 적용했으며, 서비스 담당은 점수 자체가 아니라 근거와 확인 업무가 직원 화면에 연결되도록 구현했습니다.”

## 6. 발표자 대본(약 50초)

> “저희는 통화 원문을 바로 사기 확률로 분류하지 않았습니다. 먼저 발화에서 기관 사칭, 권위·공포·긴급성 같은 심리 전략, 인증정보나 이체 요구, 금전 이동 이벤트를 구조화했습니다. 이 이벤트를 최근 10개 발화 Window 단위로 존재 여부, 반복 횟수, 다양성, 금액과 결합 신호로 집계한 뒤 Window Logistic 모델에 넣었습니다. 현재 서비스에는 실험용 artifact를 연결했고, 23개 피처 계약과 모델 해시·라이브러리 버전을 실행 전에 검증합니다. 임계값은 0.95이며, 신호가 없거나 금전 신호만 있는 경우에는 가드레일로 과도한 판정을 제한합니다. 결과는 NORMAL 또는 PHISHING 라벨만 보여주는 것이 아니라 점수·근거·모델 경고와 함께 직원의 확인 업무로 전달됩니다. 원천 데이터는 발췌 통화 776건과 자동 추출·LLM 분류 SILVER 데이터로 설명할 수 있고, RPA 수집은 실행 로그를 확인한 뒤 사실 범위에 맞게 추가하겠습니다.”

## 10. 실제로 무엇을 테스트했고 점수는 얼마였나

### 현재 저장소에서 확인되는 ML 평가

현재 확인 가능한 가장 직접적인 ML 평가는 `replay_benchmark/results/v3_0_live_20260916/deterministic_ml.json`과 `replay_benchmark/results/v3_0_core_metrics_20260916/risk_results.csv`에 기록된 **결정론적 로컬 fallback replay**다.

| 평가 항목 | 결과 | 해석 |
|---|---:|---|
| 평가 대상 | 30 cases, 160 events | `benchmark_v1.0` 시나리오에 대한 로컬 replay |
| HIGH subset recall | 10/10 = **100.0%** | HIGH 10건을 모두 `PHISHING`으로 분류 |
| HIGH/LOW precision | 10/20 = **50.0%** | HIGH 10건은 TP, LOW 10건은 FP로 분류 |
| HIGH/LOW F1 | **66.7%** | TP=10, FP=10, FN=0 기준 |
| 로컬 위험 점수 범위 | **96.18~100.00점** | 30건 모두 `PHISHING`으로 나온 fallback 결과 |
| 전체 라벨 분포 | `PHISHING 30`, `NORMAL 0` | MIXED를 포함한 전체 replay에서 모두 위험 판정 |

### 이 점수를 어떻게 설명해야 하나

이 결과는 “보이스피싱 탐지 모델의 최종 정확도”가 아니다. 기록 자체가 다음과 같이 제한되어 있다.

- 실제 provider 호출이 아니라 **로컬 결정론적 fallback + 기존 Window Logistic artifact**를 사용했다.
- HIGH/LOW 점수는 MIXED를 제외한 논리 비교이며, HIGH 10건을 놓치지 않는 대신 LOW 10건도 함께 위험으로 분류했다.
- 따라서 발표에서는 **“검증 시나리오에서 HIGH Recall 100%, HIGH/LOW Precision 50%, F1 66.7%를 기록했다”**고 쓰고, 표본·fallback·평가 범위를 각주로 붙인다.
- `0.95`는 모델 임계값이지 정확도 95%가 아니다.
- 현재 확인한 실행 셸에는 `WINDOW_RISK_THRESHOLD` override가 없어 artifact의 `0.95`가 사용된다. 다만 `MVP_v3/.env.example`에는 예시값 `0.60`이 남아 있으므로, 발표·운영 환경에서는 실제 환경변수와 artifact 임계값을 함께 기록해야 한다.

### 실제 provider 품질 평가는 아직 미완료

동일 실행 기록에서 `gold_pattern_scoring=NOT RUN`으로 남아 있다. 사유는 provider 연결 오류와 benchmark taxonomy를 모델 이벤트 family로 매핑하는 기준 미정이다. 별도 `metrics.json`도 live provider와 격리 MySQL/Docker 환경이 unavailable하여 fact precision·recall·F1을 산출하지 못했다고 기록한다.

따라서 아래 수치는 ML 위험탐지 성능으로 섞어 쓰지 않는다.

| 수치 | 정체 | 사용 범위 |
|---:|---|---|
| 126/126 = 100% | AI API 결정론적 회귀 테스트 | 계약·코드 회귀 통과율, 모델 품질 아님 |
| 146/146 = 100% | General API 비-MySQL 회귀 테스트 | API 회귀 통과율, 모델 품질 아님 |
| 14.0% Recall / 100.0% Precision / 24.6% F1 | v3.0 corrected-Gold의 30 case·100 canonical facts projection audit | LLM/Context projection 감사 결과, ML 위험탐지 점수 아님 |

### PPT에 바로 넣을 문장

> “30개 시나리오의 로컬 결정론적 replay에서 HIGH 10건은 모두 탐지해 Recall 100%를 기록했습니다. 동시에 LOW 10건도 위험으로 분류되어 HIGH/LOW Precision은 50%, F1은 66.7%였습니다. 이 결과는 실험용 Window Logistic artifact와 안전 fallback의 논리 검증이며, 실제 provider 기반 일반화 성능으로 해석하지 않았습니다.”

### 성능 수치를 최종 확정하기 위해 필요한 재시험

1. 모델 학습에 사용하지 않은 **통화 단위 독립 test set**을 고정한다.
2. 동일한 `model_features`, feature version, threshold로 Window와 통화 전체 집계를 각각 평가한다.
3. `TP/FP/FN/TN`, Recall, Precision, F1, PR-AUC와 정상 대화 오탐률을 계산한다.
4. provider를 사용하지 않는 ML 단독 평가와, LLM 이벤트 추출을 포함한 통합 평가를 분리한다.
5. 실제 서비스 artifact의 SHA-256·피처 순서·임계값이 평가에 사용한 모델과 같은지 확인한다.
