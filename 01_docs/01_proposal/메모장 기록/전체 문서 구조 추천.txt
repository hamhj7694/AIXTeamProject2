1부. 기존 현행 상황과 CSR의 서비스 취지
여기서는 기술 스택, FastAPI, MySQL 같은 말은 최대한 뒤로 빼는 게 좋아.
추천 순서는 아래야.
1-1. 현행 보이스피싱 대응 체계
먼저 기존 체계를 인정한다.
현재 보이스피싱 대응은 단말·통신 구간의 온디바이스 AI, 은행의 이상거래탐지시스템(FDS), 금융·통신·수사기관 간 정보 공유 체계인 ASAP 등 다양한 기술과 제도를 통해 이루어지고 있다.

그리고 역할을 짧게 구분.
- 온디바이스·통신사 AI: 통화·문자·악성 앱 등 위험 정황 탐지
- 은행 FDS: 거래·접속정보 기반 이상거래 탐지·제한
- ASAP: 금융·통신·수사기관 간 의심정보 공유
이 구분은 팩트체크 문서에도 동일하게 정리되어 있어.    붙여넣은 마크다운
1-2. 현행 체계의 빈틈
여기가 가장 중요해.
CSR의 문제 정의를 단순히 “시스템이 분절돼 있다”라고 쓰지 말고, 이렇게 잡는 게 좋아.
현행 체계는 위험을 탐지하는 데 강하지만, 탐지 이후 은행 직원이 실제 사건의 맥락과 진위를 빠르게 파악하는 데 필요한 정보는 충분하지 않을 수 있다.

그리고 구체화.
예를 들어 은행 직원에게 필요한 건 단순히:
“이상거래 위험이 있습니다.”

가 아니라,
누가 어떤 기관을 사칭했는가
범죄자는 어떤 논리로 고객을 설득했는가
어떤 행동을 요구했는가
송금을 요구했는가
개인정보·인증정보를 요구했는가
원격제어 앱 설치를 유도했는가
고객에게 비밀유지를 요구했는가
고객이 이미 어떤 행동을 했는가

같은 사건 맥락이야.
현재 팩트체크 문서에서도 기존 탐지 신호만으로는 고객의 현재 행동, 사칭 주체, 앱 설치, 인증정보 노출, 추가 송금 위험과 담당자의 다음 행동을 한눈에 설명하기 어렵다는 점을 문제로 정의하고 있어.    붙여넣은 마크다운
1-3. 왜 고객에게 다시 묻는 것만으로 부족한가
이 부분은 CSR 취지를 강하게 만들어줘.
탐지 이후 은행 직원은 고객에게 다시 질문해 사건 상황을 복원해야 한다.

그런데 보이스피싱 피해자는 항상 정확한 정보 제공자가 아닐 수 있어.
예:
- 범죄자를 실제 기관 직원이라고 믿고 있을 수 있음
- 본인이 속고 있다는 사실을 인지하지 못할 수 있음
- 범죄자의 “은행 직원에게 말하지 말라”는 지시를 따를 수 있음
- 송금·앱 설치·인증정보 제공의 위험성을 인식하지 못할 수 있음
- 당황하거나 혼란스러운 상태일 수 있음
따라서 문제는:
고객에게 묻는 것 자체가 아니라, 고객 답변만으로 사건을 처음부터 복원해야 한다는 점

이라고 잡으면 좋아.
1-4. 그 결과 발생하는 문제
여기서 “휴먼 에러”가 등장하면 돼.
위험 탐지
   ↓
직원이 고객에게 상황 재확인
   ↓
진위 판단
   ↓
설득
   ↓
추가 확인
   ↓
보호조치
   ↓
다른 담당자에게 인계

이 과정에서:
- 상황 파악 지연
- 반복 질문
- 담당자별 해석 차이
- 확인 누락
- 조치 누락
- 인계 과정의 정보 손실
- 고객 설득 지연
- 추가 송금 가능성
이 생길 수 있다는 논리.
여기서 표현은 “반드시 발생한다”가 아니라 “발생 가능성이 있다” 정도가 안전하다.
1-5. CSR의 서비스 취지
그리고 이제 CSR을 등장시키면 돼.
가장 좋은 정의는:
CSR은 보이스피싱을 다시 탐지하는 시스템이 아니라, 탐지 이후 은행 직원이 확인하기 어려웠던 ‘사건의 맥락’을 구조화하여 확인·설득·대응을 지원하는 AI Case Workspace이다.

조금 더 풀면:
CSR은 원문 처리 권한과 보안 통제가 확보된 단말·통신사 영역에서 분석된 통화 정황과 은행 FDS의 위험 신호, 고객 답변, 은행 확인 결과를 하나의 Shared Case로 구성한다. 이를 통해 은행 직원은 고객에게 처음부터 사건 전체를 다시 묻기보다, 이미 정리된 사건 맥락을 바탕으로 미확인 정보만 추가 확인하고 필요한 설득과 보호조치를 수행할 수 있다.

CSR이 위험 신호를 사건 맥락 → 확인 질문 → 담당자 업무 → 고객 공개 상태 → 종결 보고서로 연결하는 구조라는 점도 팩트체크 문서와 일치해.    붙여넣은 마크다운    붙여넣은 마크다운
1부를 한 문장 흐름으로 압축하면
나는 이 흐름을 추천해.
기존 체계는 보이스피싱 위험을 탐지한다 → 하지만 은행 직원에게 필요한 것은 단순 위험 신호가 아니라 범죄자의 주장·요구·압박과 고객의 실제 행동이 담긴 사건 맥락이다 → 이러한 맥락이 부족하면 직원은 고객에게 다시 상황을 확인하고 진위를 판단해야 하며, 고객 역시 범죄자의 말을 신뢰하거나 상황을 정확히 인지하지 못할 수 있다 → 그 과정에서 상황 파악·설득·인계가 지연되고 휴먼 에러와 추가 피해 가능성이 생긴다 → CSR은 탐지 이전을 대체하는 것이 아니라, 탐지 이후 필요한 통화 정황·거래 위험·고객 답변·공식 확인 결과를 하나의 Shared Case로 구조화하여 직원의 확인·설득·대응을 지원한다.

이게 1부의 전부라고 생각하면 돼.
2부. 적합성 — 기획·개발·운영 계획
여기서는 감성적 문제 제기는 끝내고 기술·실현 가능성으로 넘어가야 해.
한글 문서라면 나는 다음 7개 소제목으로 구성하겠어.
2-1. 서비스 구현 범위 및 전체 아키텍처
첫 문장:
CSR은 외부 탐지 시스템이 생성한 위험 신호를 수신하고, 사건 맥락을 구조화하여 Shared Case를 생성한 뒤, 고객과 은행 담당자의 확인·대응 업무를 지원하는 구조로 설계하였다.

그다음 전체 구조:
외부 위험 신호
온디바이스 · 통신사 · FDS · ASAP
        ↓
표준화된 구조화 데이터 수신
AnalysisEnvelope
        ↓
사건 분석 및 Shared Case 구성
        ↓
은행 Case Room
고객 지원 화면
        ↓
질문 · 확인 · 업무 · 인계 · 보고

현재 실제 구조는 Frontend → General API → AI API → MySQL 중심으로 구현되어 있고, AI API에는 Diagnosis, CaseCopilot, Customer Support, Question/Work Card, Final Report, Quality Guard가 분리돼 있어.    붙여넣은 마크다운
2-2. 외부 시스템 연동 설계
여기서는 세 축으로 나누면 된다.
A. 온디바이스·통신사
CSR이 통화 원문을 직접 수집하지 않고, 외부 분석 모듈에서 생성된 구조화 신호를 전달받는다.

핵심 기술:
- AnalysisEnvelope
- source
- timestamp
- actor
- impersonation
- request/action
- amount
- app installation
- credential exposure
- confidence
- source reference
현재 문서에서는 원문 없는 analysis-envelope.v1을 기반으로 외부 연동을 설계하도록 되어 있어.    붙여넣은 마크다운
B. 은행 FDS
초기에는 read-only Adapter 방식으로 탐지 이벤트를 전달받는다.

여기서 중요한 건:
CSR이 FDS를 다시 계산하지 않는다.
FDS 결과를 하나의 사건 근거로 받아 활용.
C. ASAP
허용된 의심정보를 Case의 근거 또는 기관 확인 맥락으로 참조한다.

역시 대체가 아니라 연동.
2-3. 데이터·보안·망분리 설계
이건 적합성에서 반드시 있어야 해.
나는 3단계 보안 구조로 쓰는 게 제일 좋다고 봐.
1단계 — Edge 최소화
단말·통신사 영역에서:
- 통화 원문 분석
- 개인정보 최소화
- 계좌·전화·인증정보 제거
- 구조화 Event 생성
↓
2단계 — Bank Private AI
은행 내부망:
- 구조화 신호 검증
- Shared Case 구성
- 내부 sLLM 요약
- 질문 추천
- 대응 업무 제안
↓
3단계 — Human-controlled Workspace
은행 직원:
- 근거 확인
- 미확인 정보 확인
- 고객 설득
- 업무 수행
- 공식 조치 승인
이 3단계 구조는 첨부 문서에 그대로 정의되어 있어.    붙여넣은 마크다운
