## 문서 목적

2026년 9월 3일의 1차 목표는 하나의 Case를 중심으로 은행 대응, 고객 상담, 기관 검증이 연결되되 각 화면에는 업무 목적에 맞는 정보만 노출되도록 기준을 정립하고 구현을 시작하는 것이다.

이 문서는 `new_md/01_PRD.md`, `02_TODO.md`, `03_WORK_MAPPING.md`, `04_WORK_RULES.md`를 상위 기준으로 한다. 완료 작업의 시점별 기록은 같은 폴더의 `260903_part1_rog.md`에서 관리한다.

## 1차 목표

### 1. 공통 Case와 메시지 계약

- 모든 화면이 동일한 Case 기준 정보(ID, 담당자, 피해 여부, 실제 피해 금액, 사기 유형, 업무 상태, 생성일, 최근 업데이트)를 사용한다.
- 메시지는 작성자 ID, 표시 이름, 역할, 공개 범위, 유형, 답글 연결 정보를 가진다.
- 말풍선은 메시지 역할이 아니라 **현재 접속한 사용자 본인 여부**로 좌·우를 결정한다.
- 시스템 이벤트는 채팅이 아닌 Case Live Log에서만 확인한다.

### 2. 은행 대응 화면

- 팀 작업과 AI 개인 업무 대화는 데이터·공개 범위를 분리한다.
- 기본 은행 협업 화면에서는 팀 대화와 팀에 공유된 AI 답변을 하나의 협업 흐름으로 확인한다.
- AI는 `@CaseCopilot`, 명시적 AI 요청 버튼, 개인 AI 작업공간에서만 응답한다.
- 개인 AI 분석 초안은 명시적으로 공유한 경우에만 팀 대화·보고서 근거에 포함한다.
- Live Log와 우선 조치/위험요소는 채팅 좌측 고정 영역에서 관리한다.
- Case 허브의 중복된 업무 안내는 두지 않고 은행 화면의 `우선 조치 및 위험요소`로 통합한다.

### 3. 고객 상담 화면

- 고객은 안전 안내, 현재 상황 입력, 피해 정보 확인에 집중한다.
- 고객 메시지만 오른쪽에 표시하고, Customer Agent 및 고객 공개가 허용된 은행 안내는 왼쪽에 표시한다.
- 고객 화면에는 은행 팀 채팅, AI 내부 분석, 내부 검증 요청·근거, 내부 위험 점수·조치 계획을 노출하지 않는다.
- 피해 여부, 실제 피해 금액, 송금 진행, 원격제어 앱, 제공 정보, 사칭 대상, 상담 상태는 후속 구조화 문진으로 DB에 저장한다.

### 4. 기관 검증 화면

- 검증 Task는 대상 → 주장/근거 → 공식 채널 확인 → 결과/근거 저장 → Case 반영 흐름을 따른다.
- Task에 대상 유형, 우선순위, 담당자, 기한, 결과, 결과 요약, 확인 시각, 확인자, 근거, RAG 출처, 고객 공개 가능 여부를 관리한다.
- 실제 외부 기관 전송 기능이 구현되기 전에는 “공식 채널 확인 업무 기록”으로 명확히 표시한다.

### 5. 데이터·보안·보고서 원칙

- 고객/은행/검증은 역할별 Bundle과 권한으로 분리한다.
- AI 추천과 사람이 확정한 검증 결과를 구분한다.
- RAG 결과에는 출처, 적용 범위, 최신성, 사람 확인 필요 여부를 저장한다.
- 보고서·휴지통·버전 이력은 브라우저 저장소가 아닌 SQLite DB/API를 단일 원본으로 사용하도록 전환한다.
- 실제 인증/RBAC 도입 전에는 MVP 데모용 화면 경계로 운영하며, 클라이언트 요청의 사용자 정보를 신뢰하지 않는 서버 인증 구조를 후속으로 구현한다.
