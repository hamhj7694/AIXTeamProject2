# MVP_v2 작업 규칙

## 기준 문서

작업 전 new_md/01_PRD.md와 new_md/02_TODO.md를 읽는다. 요구사항, 코드, 문서가 충돌하면 임의로 결정하지 말고 Orchestrator와 Product에 알린다.

## 데이터 규칙

- 목록에 통화 원문 전문이나 불필요한 개인정보를 노출하지 않는다.
- 피해 여부, 실제 피해 금액, 요구 금액은 다른 데이터다.
- 확인되지 않은 값은 확인안됨으로 표시하며 피해 없음으로 추정하지 않는다.
- 모든 Case 화면은 동일 Case API 데이터를 사용한다.

## 계약과 저장소 규칙

- 공개 API 변경은 contracts/public_api부터 변경한다.
- API 필드 변경 시 Frontend service와 계약 테스트를 같은 작업에서 바꾼다.
- SQLite는 로컬 MVP 기본이다. MySQL 경로도 계약이 깨지지 않게 유지한다.
- 팀이 공유해야 하는 데이터는 최종적으로 DB API에 저장한다. localStorage는 임시 구현으로 문서에 표시한다.

## AI 규칙

- AI는 구조화된 계약을 반환하고 화면 문구를 직접 소유하지 않는다.
- AI 위험 점수는 근거이며, 금융 조치와 사건 종료는 사람이 최종 결정한다.
- RAG 응답에는 출처, 적용 범위, 확인 필요 여부를 남긴다.
- 은행 팀 채널 AI는 명시적 멘션/호출에만 응답한다.

## UI/UX 규칙

- 목록 기본 정렬은 최근 업데이트 내림차순이다.
- 상태는 내부 코드가 아니라 한글 업무 상태로 표시한다.
- 삭제와 휴지통을 구분하고 보관 기한과 복구 가능 여부를 명시한다.
- 위험한 동작에는 확인 단계를 둔다.

## 검증과 완료

- Frontend 변경 후 npm run build를 실행한다.
- Backend/AI 변경 후 관련 테스트를 실행한다.
- 실행 중인 API는 코드 변경 후 재시작 여부를 확인한다.
- 완료 보고에는 변경사항, 검증 결과, 남은 제약을 함께 기록한다.
- 완료는 [x], 부분 구현은 [-]로만 표시한다.

## 점검과 디버깅

- 점검 담당자는 은행·고객·검증·목록 화면을 사용자 역할별로 확인하며, 내부 정보 노출, 중복 정보, 다음 행동의 명확성, 상태 문구, 빈 상태, 오류 상태를 점검한다.
- 점검 결과는 `재현 경로 → 기대 결과 → 실제 결과 → 사용자 영향 → 제안` 순서로 기록한다.
- 디버깅 담당자는 오류를 재현한 뒤 원인을 API 계약, 저장소 데이터, 서버 로그, 프론트 상태 중 하나로 좁힌다. 추측만으로 수정하지 않는다.
- 디버깅 수정은 최소 범위로 적용하고, 관련 단위 테스트·빌드·수동 경로를 모두 다시 검증한다.
- 비밀값, 통화 원문, 개인정보는 로그나 이슈 기록에 그대로 남기지 않는다.
