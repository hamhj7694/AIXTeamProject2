# CONTEXT-FIRST CASE — MVP v2 제품 요구사항 정의서(PRD)

작성일: 2026-09-03

문서 목적: MVP_v2의 제품 정의, 사용자 역할, 화면 구조, 데이터 계약, AI/ML/RAG 동작 방식, 현재 구현 상태, 미완료 범위, 완료 기준을 하나의 기준 문서로 정리한다. 이 문서는 상위 제품 기준이며, 세부 구현 변경 시 02_TODO.md, 05_DATA_SCHEMA_AND_FLOW.md 등 원본 문서를 함께 갱신한다.

# 1. 제품 한 줄 정의

> 의심 통화를 문장별 ML과 전체 맥락 분석으로 탐지한 뒤, 하나의 Case를 중심으로 고객·은행 담당자·기관 검증 담당자·AI가 역할별로 상담·질문·검증·보호조치·보고를 이어가는 보이스피싱 대응 협업 플랫폼.

# 2. 제품 배경과 문제 정의

## 2.1 우리가 해결하려는 문제

기존 대응체계는 통화 위험 탐지, 위험정보 공유, 이상거래 탐지·보호와 같은 기능을 수행하지만, 실제 사건이 발생한 뒤에는 담당자가 사건 맥락을 파악하고 고객에게 사실관계를 확인하며 필요할 경우 설득까지 해야 한다. 고객 역시 사기범이 만든 판단환경 안에서 자신의 상황을 정확히 설명하기 어렵거나 사기를 부인할 수 있다.

- 탐지 결과(Alert)만으로는 "누가 무엇을 주장했고 무엇을 요구했는지"라는 사건 맥락을 완전히 설명하기 어렵다.
- 은행 담당자는 여러 정보와 고객 응답을 다시 종합해 사건을 이해하고 확인 방향을 정해야 한다.
- 고객에게 질문한다고 해서 곧바로 사실 확인이 끝나는 것은 아니며, 설득과 추가 검증이 필요한 경우가 있다.
- 여러 담당자와 화면을 오가며 같은 사건을 반복 설명·정리하면 업무 흐름이 끊기고 최신 상태 파악이 어려워질 수 있다.
- 피해 발생 이후 신고·지급정지·피해구제로 넘어갈 때도 예방 단계에서 확보한 사건 맥락과 기록을 재사용할 필요가 있다.

## 2.2 제품이 선택한 해결 원칙

- 탐지 정확도 자체를 차별점으로 두지 않는다.
- 탐지 이후의 실시간 정보 수집, 사건 맥락 재구성, 진위 확인, 고객 설득, 업무 인수인계를 하나의 Case에서 연결한다.
- 고객과 은행은 같은 사건 데이터를 공유하되, 역할과 권한에 따라 서로 다른 공개 범위를 본다.
- AI는 최종 판단자가 아니라 확인·검증·설득을 위한 업무 지원자다.
- Chat-first UX를 사용하되, 내부 데이터는 메시지·질문·검증·조치·상태변경 등 구조화된 형태로 저장한다.
- 피해 예방과 피해구제를 분리된 시스템으로 보지 않고 같은 Case와 Timeline으로 이어간다.

# 3. 제품 목표와 비목표

## 3.1 MVP v2 목표

- 의심 통화 입력부터 Case 생성까지 자동화된 데모 흐름을 구현한다.
- 고객 상담, 은행 내부 협업, 기관 검증을 하나의 Case에서 분리된 채널로 운영한다.
- CaseFact, Verification, Bank Action, Event를 구조화해 사건 상태를 추적한다.
- AI가 질문·Brief·검증·설득을 제안하되 담당자 검토와 승인 경계를 명확히 한다.
- 피해 발생 시 같은 Case를 Recovery Mode로 전환해 기존 기록을 재사용한다.
- 실제 금융·통신 API 연동 전에도 전체 사용자 경험과 업무흐름을 검증할 수 있는 MVP를 완성한다.

## 3.2 MVP v2 비목표

- 실제 통신사 통화 원문을 실시간 수집하는 기능
- 실제 FDS/ASAP 운영망과의 직접 연동
- AI가 자동으로 금융거래를 차단·해제하는 기능
- AI가 담당자 승인 없이 고객에게 메시지를 자동 발송하는 기능
- 외부 수사·공공기관 시스템에 자동 검증 요청을 보내는 기능
- 실제 상용 인증/RBAC를 완성하는 것(후속 범위)

# 5. End-to-End 제품 흐름

> 텍스트 입력 → 문장별 ML/전체 맥락 분석 → 임계값 판정 → Case + 초기 Brief 생성 → 고객 상담 / 은행 협업 / 기관 검증 → CaseFact·검증 근거·은행 조치 누적 → 담당자 승인·보고서 확정·사건 종료

## 5.1 단계별 정의

| 단계 | 입력 | 시스템 처리 | 주요 출력 |
| --- | --- | --- | --- |
| 1. 입력 | 의심 통화 텍스트 | 문장 분리, 문장별 위험 분석 준비 | 문장 단위 데이터 |
| 2. 탐지 | 문장별 Feature/ML 점수 | 문장별 ML 위험 융합, 최고 위험 점수 계산 | 위험 점수, 근거 Feature |
| 3. Case 생성 | 임계값 이상 탐지결과 | 순번 Case ID 생성, 초기 Brief/State 생성 | Case, 초기 Event, 초기 Brief |
| 4. 고객 상담 | 고객 공개 질문/메시지 | 필수 질문 응답, 피해 여부·행동 상태 수집 | 고객 응답, 고객 공개 메시지 |
| 5. 은행 협업 | Alert, 거래정보, 고객응답 | 사건 Brief, 질문/확인계획, CaseFact 후보 생성 | 은행 내부 메시지, 질문카드, 후보 Fact |
| 6. 기관 검증 | 사칭기관, 범죄자 주장 | 공식 절차·근거 비교, 검증 상태 저장 | Verification Result/Evidence |
| 7. 보호조치 | 확정 Fact, 검증, 고객상태 | 담당자 검토 후 조치 기록 | Bank Action, State 변화 |
| 8. 종료/복구 | 피해 여부와 최종상태 | Case Closed 또는 Recovery Mode 전환 | 보고서, Recovery workflow |

# 6. 핵심 UX 원칙

## 6.1 Chat-first — 채팅이 서비스의 기본 작업 인터페이스

이 서비스에서 채팅은 단순 상담 UI가 아니라 **대부분의 조회·확인·요청·정보공유·CRUD·업무 실행이 시작되는 기본 작업 인터페이스**다. ChatGPT처럼 사용자는 별도 메뉴를 계속 이동하기보다 Case 채팅 안에서 자연어 대화와 실행형 카드를 통해 사건을 처리한다.

- 정보 조회: "현재 확인된 사실 보여줘", "기관 검증 결과 알려줘", "최근 조치 정리해줘"처럼 채팅에서 요청한다.
- 정보 생성: 고객 질문, 내부 메모성 메시지, 검증 요청, 조치 요청, CaseFact 후보 등을 채팅에서 생성한다.
- 정보 수정·확정: AI가 제안한 Fact·질문·조치 카드를 담당자가 채팅 안에서 수정·승인·확정한다.
- 상태 변경: 확인 완료, 검증 요청, 보호조치 검토 등 업무 상태 변경을 채팅의 실행형 카드와 명시적 액션으로 수행한다.
- 정보 공유: 은행 내부, 고객 공개, 기관 검증 등 공개 범위를 지정해 동일 Case 안에서 전달한다.
- 정보 탐색: 중요한 과거 메시지는 북마크·Live Log·검색을 통해 다시 찾고 원문 메시지로 즉시 이동한다.

단, 모든 기능을 억지로 말풍선으로 표현하지 않는다. **채팅이 명령·상호작용의 중심**이고, Case List·Timeline·진행 스테퍼·개인 메모·북마크·보고서처럼 지속적으로 확인해야 하는 정보는 채팅 주변의 보조 UI로 제공한다. 내부 데이터는 Message, Question, Fact, Verification, Action, Bookmark, PersonalNote, Event 등 구조화 객체로 저장한다.

## 6.2 고객 화면 최소화

- 위험 행동 중단, 현재 상황 설명, 필수 질문 응답, 진행 상태 확인에 집중한다.
- 내부 분석 정보와 기술적 지표는 노출하지 않는다.
- 고객이 지금 해야 할 행동과 다음 단계만 간결하게 안내한다.
- 고정 피해구제 안내를 제공하고, 사용자의 요청은 Case 메시지/이벤트로 기록한다.

## 6.3 은행 화면: 외부 대화와 내부 업무 분리 + 개인 작업 보조

- 고객 대화, 은행 내부 협업, AI 개인 작업공간을 명확히 구분한다.
- AI는 멘션·빠른 작업·명시 요청에만 반응한다.
- 추천 질문·직접 질문·기관 확인·미확인 정보는 채팅 안의 실행 가능한 카드로 제공한다.
- AI 제안은 담당자 검토·승인 후에만 고객에게 전달된다.
- **개인 메모 공간(Personal Memo)**을 제공한다. 메모장/온라인 포스트잇처럼 담당자 개인이 사건을 보며 임시 생각, 확인할 내용, 콜백 메모, 업무 체크를 자유롭게 기록한다.
- 개인 메모는 기본적으로 작성자 본인에게만 보이며, 공식 CaseFact·고객 메시지·기관 검증 결과와 구분한다. 필요 시 명시적 액션으로 내부 공유 또는 Fact 후보로 전환할 수 있다.
- **메시지 북마크(Bookmark)**를 제공한다. 담당자는 고객·내부·AI 채팅의 중요한 메시지/카드를 북마크할 수 있다.
- 북마크는 Case별 바로가기 리스트에 누적되며, 항목을 클릭하면 해당 채널의 원본 메시지 위치로 즉시 스크롤/이동한다.
- 북마크에는 메시지 요약, 작성자/채널, 생성시각, 북마크 메모(선택)를 표시하고 해제할 수 있다.

## 6.4 사건 상태와 Timeline 우선

고정형 보고서 패널 대신 Case Live Log를 사용해 사건 발생, 질문, 검증, 조치, 상태 변경을 시간순으로 기록한다. 담당자는 최신 진행상황과 판단 근거를 재정리하지 않고 추적할 수 있어야 한다.

## 6.5 10초 안에 이해되는 Shared Case

- 모든 핵심 화면과 AI 출력은 `현재 상황 → 확인된 사실/미확인 정보 → 지금 할 일 → 실행 결과` 순서의 정보 위계를 사용한다.
- 통화·신고 맥락, 고객 응답, 은행 Case 정보, 기관 검증 결과는 복제된 별도 문서가 아니라 같은 `case_id`의 출처가 있는 Context로 연결한다.
- AI 카드에는 참고한 맥락 출처와 다음 행동을 명시하고, 입력에 없는 사실을 채우지 않는다.
- 고객 문구는 불안을 키우는 내부 용어 대신 즉시 중단할 행동과 안전한 다음 단계를 제시한다.
- 은행 문구는 판단 주체·근거·미확인 상태·승인 필요 여부를 분리해 담당자가 빠르게 검토하고 실행할 수 있게 한다.
- 색상은 장식보다 공개 범위와 상태를 구분하는 데 사용한다. 내부 작업은 어두운 중립색, 고객 공개는 밝은 색, 위험/긴급은 제한된 적색, 완료는 녹색을 사용한다.

# 7. 최종 화면 요구사항

## 7.1 Case 목록

- 실제 API의 Case만 표시한다.
- 필수 컬럼: ID, 담당자, 피해 여부, 피해 금액, 사기 유형, 업무 진행 상태, 최초 생성일, 최근 업데이트, 사건 요약.
- 기본 정렬: 최근 업데이트 최신순.
- 컬럼 정렬 토글, 검색, 필터, 휴지통을 제공한다.
- 담당자가 없으면 "미배정"으로 표시한다.
- 향후 모바일에서는 카드형 목록을 지원한다.

## 7.2 Case 개요

- Case 공통 요약, 고객 상태, 담당자/참여자, 확정 정보, 최근 이벤트를 제공한다.
- 은행 대응, 고객 상담, 기관 검증 화면으로 이동할 수 있어야 한다.
- 화면별로 서로 다른 Case 복사본을 만들지 않고 동일 Case 데이터를 공유한다.

## 7.3 고객 상담

- 고객에게는 customer-public 메시지와 구조화 질문 카드만 노출한다.
- 채팅 외부에 "상황 접수 → 피해 여부 확인 → 기관 확인 → 보호 조치 → 처리 완료" 스테퍼를 제공한다.
- 고정 피해구제 메뉴: 즉시 연락, 증빙 확보, 신고 접수, 구제 신청.
- 피해구제 항목 클릭 시 상세 절차를 열고, AI 조언 또는 담당자 대행 요청을 Case 메시지로 남긴다.
- 내부 협업 대화, 검증 내부근거, AI 위험 점수는 노출하지 않는다.

## 7.4 은행 대응

은행 대응 화면은 **채팅을 주 작업공간**으로 하고, 주변에는 채팅을 보조하는 최소한의 고정 도구만 둔다.

- 채널을 최소 3개로 구분: 은행 내부 협업 / 고객 대화 / AI 개인 작업공간.
- 질문 생성, 기관 확인 요청, Fact 후보 확인, 고객 전달, 조치 요청, 결과 확인 등 대부분의 업무를 채팅 또는 채팅 안 실행형 카드에서 처리한다.
- 채팅 왼쪽 또는 인접 영역에 사건 진행 Timeline, 우선 조치, 위험요소를 제공한다.
- 참여자, presence, 열람자, 담당자를 관리한다.
- 추천 질문, 직접 질문, 기관 확인, 미확인 정보는 카드형 작업으로 실행한다.
- CaseFact 후보를 검토하고 확정한다.
- 보고서 생성·버전·확정·휴지통을 관리한다.

### 7.4.1 개인 메모 공간

- Case별·담당자별 개인 메모 공간을 제공한다.
- UI는 작은 메모장 또는 온라인 포스트잇처럼 즉시 작성·수정·삭제할 수 있어야 한다.
- 예: "고객이 14시에 다시 통화 가능", "앱 설치 여부 재확인", "기관 검증 결과 나오면 설득 포인트로 사용".
- 자동 저장을 기본으로 하며 Case 이동 후 다시 돌아와도 유지한다.
- 기본 공개 범위는 `private-to-author`이다.
- 메모는 공식 사건 사실로 자동 승격되지 않는다.
- 담당자가 선택한 경우에만 내부 공유 메시지 또는 CaseFact 후보로 전환한다.

### 7.4.2 채팅 북마크 / 바로가기 리스트

- 모든 주요 메시지와 실행형 카드에 북마크 버튼을 제공한다.
- 북마크 시 `case_id`, `user_id`, `message_id 또는 target_object_id`, `channel`, `created_at`, `note(optional)`를 저장한다.
- 은행 화면에 현재 Case의 북마크 리스트를 항상 접근 가능한 형태로 제공한다.
- 북마크 항목을 클릭하면 해당 채널로 전환하고 **원본 메시지/카드 위치로 즉시 이동 및 강조 표시**한다.
- 고객의 핵심 진술, AI가 제안한 중요한 질문, 기관 검증 결과, 조치 결정 근거 등을 빠르게 다시 찾는 용도로 사용한다.
- 북마크 추가/해제는 원본 메시지를 수정하지 않으며 개인 북마크를 기본값으로 한다.
- 향후 필요 시 `팀 공유 북마크`를 별도 권한으로 확장할 수 있다.

## 7.5 기관 검증

- 검증 대상과 사칭 주장을 등록한다.
- 결과 필드: 결과 요약, 확인자, 근거 URL, RAG 출처, 고객 공개 여부.
- MVP에서는 외부 기관에 자동 요청하지 않고 내부 업무 기록으로 관리한다.
- 검증 결과는 동일 Case의 Verification Evidence로 저장한다.

# 9. AI / ML / RAG 구조

## 9.1 ML 역할

- 입력 텍스트를 문장 단위로 분리한다.
- 문장별 Feature를 이용해 위험도를 계산한다.
- 전체 통화에서 최고 위험 점수와 보조 신호를 융합해 임계값을 판정한다.
- 임계값을 넘으면 Case 생성 Trigger를 발생시킨다.

## 9.2 LLM/Agent 역할

- Customer Agent: 고객 상황 브리핑, 노출 질문 순서, 피해발생 여부 질문/제안, 고객 공개 메시지 초안.
- Bank Agent: FDS/거래위험 분석, 통화맥락 Brief, 확인계획·질문·설득 초안.
- Verification Agent: 사칭기관·공식절차·범죄자 주장 비교, 근거 기반 검증.
- Case Orchestrator: Event와 Case State에 따라 필요한 Agent/작업/병렬업무를 선택하고 Timeline을 통합.

## 9.3 RAG 역할

RAG는 예방·확인·설득·피해구제 단계에서 검증된 운영 지식을 제공한다. 최종 RAG 지식베이스는 PREVENT 6개 모듈과 RECOVERY 6개 모듈을 기본 Taxonomy로 삼고, 상황·확인사항·고객질문·검증근거·은행대응·기관연계·다음 단계·출처를 구조화한다.

# 10. Shared Case 데이터 모델

채팅 화면의 텍스트를 단순 로그로 저장하지 않는다. 각 상호작용은 목적에 맞는 구조화 객체로 저장하고, 화면은 동일 Case의 역할별 View를 렌더링한다.

# 11. Case State와 업무 흐름

## 11.1 기본 상태

> 상황 접수 → 피해 여부 확인 → 기관 확인 → 보호 조치 → 처리 완료

## 11.2 시스템 상태 예시

- NEW / DETECTED: 위험 Event로 Case가 생성됨.
- ASSESSING: 은행이 사건 맥락과 고객 상태를 파악 중.
- CUSTOMER_CHECK: 고객 질문·응답 진행 중.
- VERIFYING: 기관·절차·주장 검증 중.
- PROTECTING: 거래중지·추가 확인 등 보호조치 검토/진행.
- CASE_CLOSED: 피해 차단 또는 정상 확인으로 종료.
- RECOVERY_MODE: 피해 발생 확인 후 신고·지급정지·피해구제 흐름으로 전환.

# 12. PREVENT / RECOVERY 운영 범위

## 12.1 PREVENT

- 송금·이체 중단 및 추가 확인
- 사칭 주체·요구사항 진위 확인
- 고객 상황·통화 맥락 확인
- 추가 피해 행동 차단
- 고객 설득 및 안전행동 안내
- 은행·기관 간 확인 및 보호조치 연계

## 12.2 RECOVERY

- 지급정지 및 추가 자금이동 차단
- 112 신고 및 사건 접수
- 피해구제 절차 안내·신청 지원
- 증거·기록 보존
- 계정·기기·금융보안 복구
- 후속 모니터링 및 Case 관리

Recovery Mode는 기존 112·피해구제 체계를 대체하지 않는다. 예방 단계에서 확보한 Case 맥락, 검증 결과, Timeline을 재사용해 피해 이후 대응을 빠르게 이어주는 역할을 한다.

# 13. 공개 범위와 권한 원칙

- 고객은 customer-public 메시지, 본인 질문/응답, 공개 검증 결과, 진행 상태만 본다.
- 은행은 고객 대화와 내부 협업/AI 공간을 분리해서 본다.
- 기관 검증 담당자는 검증에 필요한 최소 Case 정보만 본다.
- AI는 화면상 권한과 동일한 데이터 경계를 따라야 한다.
- 모든 고객 전달 메시지는 담당자 검토/승인 정책을 적용한다.
- AI는 데이터베이스를 직접 수정하지 않으며, 백엔드 계약을 통해서만 상태변경이 반영된다.

# 14. 실제 구현 전제조건

실제 서비스 도입 시 기존 통신 AI·ASAP·FDS 정보를 단순 연결하는 것만으로는 충분하지 않다. 통화 원문 전체를 직접 외부 공유하지 않는 제약을 전제로, 통신사 AI가 사건 맥락 재구성에 필요한 구조화 Feature를 새로 생성·전달하는 체계가 필요하다.

## 14.1 통신사 AI에서 필요한 Context Feature 예시

- 사칭 주체
- 범죄자 주장(Claim)
- 요구 행동(Demand)
- 압박·긴급성
- 고립 유도
- 금액·계좌·기관명
- 위험 발화 구간
- 발화 순서·Timeline

## 14.2 결합할 금융·외부 정보

- FDS: 거래금액, 신규수취인, 탐지 Rule, 이상거래 점수/상태, 거래 지연·정지 상태 등
- ASAP: 위험계좌·피해의심·악성앱·공유 위험신호 등
- 기관 검증: 공식 절차·기관정보·근거 URL/RAG 출처

## 14.3 필요한 연계 원칙

- 공통 Case ID 또는 사건 연계 키
- 구조화 Context Feature Schema
- 실시간 또는 준실시간 Event 전달 API
- 최소정보 제공과 역할별 접근권한
- 감사 가능한 Event Log

# 17. MVP 완료 기준(Acceptance Criteria)

- 의심 통화 텍스트 입력 후 임계값 조건에 따라 실제 Case가 생성된다.
- 생성된 Case가 목록·개요·고객·은행·검증 화면에서 동일한 데이터로 일관되게 표시된다.
- 고객에게는 허용된 공개 메시지/질문만 보이고 내부 데이터는 노출되지 않는다.
- 은행 담당자는 AI가 제안한 질문/메시지를 검토한 후 고객에게 전달할 수 있다.
- 검증 결과가 결과 요약·근거 URL·RAG 출처·공개 여부와 함께 Case에 저장된다.
- CaseFact 후보가 담당자 확정 후 Case 상태/목록/보고서에 반영된다.
- 주요 메시지·검증·조치·상태 변경이 Case Live Log에 시간순으로 기록된다.
- 피해 발생 시 동일 Case가 Recovery Mode로 전환되어 예방 단계 기록을 재사용한다.
- AI가 직접 DB를 수정하거나 승인 없이 고객 메시지를 발송하지 않는다.
- 프론트 프로덕션 빌드와 API health가 통과하고, 핵심 End-to-End 시나리오가 재현된다.

# 18. 핵심 시연 시나리오

1. 의심 통화 텍스트 입력: 검찰 사칭, 범죄 연루 주장, 안전계좌 송금 요구가 포함된 시나리오
1. ML 위험 점수가 임계값을 넘어 Case 생성
1. Case Orchestrator가 초기 Brief와 고객 질문을 준비
1. 고객 화면에서 필수 질문 응답 및 "추가 송금 중단" 안내 확인
1. 은행 화면에서 고객 응답과 AI Brief 확인, 질문/검증 요청 검토
1. Verification에서 공식 절차와 범죄자 주장을 비교해 결과 등록
1. 은행 담당자가 결과를 바탕으로 고객 설명/설득 메시지 승인
1. Bank Action/Case State 변경 및 Live Log 기록
1. 피해 없음이면 Case Closed, 피해 확인이면 Recovery Mode 전환

# 2026-09-03 범위 확정 부록

## 음성 통화 상담 — 후속 확장 기능

현재 MVP에서는 음성 통화 상담을 실제 구현하거나 시연하지 않는다. WebRTC/전화 연결, 통화 녹음, 실시간 STT, 화자 분리, 음성 파일 분석, 상담원 통화 제어는 모두 후속 확장 범위다. 현재 실제 라우트의 은행·고객 화면은 텍스트 채팅과 구조화 카드만 사용한다. 저장소에 남아 있는 기존 `VoiceCallPopup`·voice API 코드는 현재 라우트에 연결하지 않으며, 완료 항목으로 계산하지 않는다.

음성 기능을 다시 시작할 때는 별도 PRD와 동의·보존기간·접근권한·암호화·마스킹·감사 로그·녹음 고지 정책을 먼저 확정한다. 음성 기능이 없어도 Case 생성 이후 고객 질문, 은행 협업, 기관 검증, 첨부파일, 보고서, 피해구제 흐름은 독립적으로 완성되어야 한다.

## 파일·이미지 첨부

텍스트 채팅은 이미지와 허용 문서 파일을 첨부할 수 있다. 파일 원본은 서버의 Case별 안전 경로에 저장하고, DB에는 원본명·서버 상대 경로·MIME·크기·해시·공개 범위·업로더·메시지 연결 상태를 저장한다. 고객 공개 파일과 은행 내부/AI 개인 파일은 같은 공개 범위 규칙을 따른다. AI는 향후 권한이 허용된 첨부만 읽으며, OCR·문서 파싱·악성 파일 검사·RAG 색인은 후속 구현이다.

## 사용자 정보 위계 원칙

- 고객 화면의 한 카드에는 하나의 핵심 질문만 크게 표시한다. 같은 의미의 설명을 제목 아래 반복하지 않는다.
- 고객은 `지금 멈출 행동 → 현재 질문 → 선택/입력 → 다음 진행 단계` 순서로 읽는다. 은행 내부 사유·위험점수·기술 상태는 고객 화면에서 제거한다.
- 은행 직원은 `가장 먼저 할 일 → 고객 응답 대기 → 위험요소 → 근거/이력` 순서로 읽는다. 첫 업무는 크기와 명도로 확실히 강조한다.
- AI 결과는 `Shared Case 맥락 → 상황 요약 → 판단 근거 → 지금 할 일 → 실행 입력` 순서로 표시한다. 모델명과 내부 상태는 보조 계층으로 둔다.
- 고객 전용 화면은 은행 목록·Case Hub·은행 대응·기관 검증 내비게이션을 포함하지 않는다.
- 카드 생성·실행·고객 전달·고객 답변은 시간순 업무 이력으로 복원 가능해야 한다. 임시 편집 카드는 성공 후 닫되 결과는 사라지지 않는다.
